# Transit Hub: проверка основного этапа

Этот сценарий отделяет **официальное архивное воспроизведение** от отдельной проверки бинарного NDTP-эмулятора. Учебный план для NDTP не является актуальным расписанием Москвы и не используется для оценки MAE.

## 1. Четыре сервиса и официальный архив

Нужны Docker Compose, Node.js 22+, Python 3 и доступ к [архиву организаторов](https://disk.yandex.ru/d/CA6tsj4aJJ4Aaw). Сырые данные и образ эмулятора в Git не включены; веса модели уже в репозитории.

```sh
python3 scripts/prepare-official-data.py --save-archive ml/data/official-dataset.zip
export API_TOKEN="$(openssl rand -hex 32)"
node scripts/start-official-docker.mjs -d
docker compose -f compose.official.yaml ps
```

В Windows PowerShell те же действия выполняются так (Docker Desktop должен быть запущен в режиме Linux-контейнеров):

```powershell
python scripts/prepare-official-data.py --archive 'C:\path\dataset.zip'
$env:API_TOKEN = node -p "require('node:crypto').randomBytes(32).toString('hex')"
node scripts/start-official-docker.mjs -d
docker compose -f compose.official.yaml ps
```

Перед первой сборкой оставьте не менее 10 ГБ свободного места на диске с хранилищем Docker. Точное потребление зависит от кэша и архитектуры. При `read-only file system` проверьте свободное место и состояние Docker: это ошибка хранилища, повтор установки зависимостей её не исправит. После аварийного завершения процесса контейнеры перезапускаются автоматически; явный `docker compose stop` сохраняет остановку. Docker-журналы ограничены тремя файлами по 10 МБ на сервис.

После запуска для повторяемой локальной нагрузки через адрес жюри выполните `pnpm install --frozen-lockfile`, затем `node scripts/benchmark-jury-stress.mjs`. По умолчанию проверка длится три минуты, использует 25 WebSocket-клиентов и 8 HTTP-работников с паузой 200 мс. Результат сохраняется в `reports/jury-stress.json`; при ошибке HTTP, потере потока или отсутствии heartbeat команда завершается с ненулевым кодом. Проверка разрешает только localhost и не должна запускаться на чужом оценочном стенде.

При наличии ZIP скачивание можно заменить на `python3 scripts/prepare-official-data.py --archive /путь/к/архиву.zip`; для пункта 3 ниже сохраните этот ZIP как `ml/data/official-dataset.zip`. Ожидаются четыре контейнера `frontend`, `api`, `backend`, `ml`; три серверных имеют статус `healthy`.

- [Обзор сети](http://127.0.0.1:8080/overview?source=official): GPS-позиции, доступные прогнозы, целевые остановки, риск и алерты. Время — из CSV, **06.01.2026**, а не текущее время Москвы.
- [Диспетчерская](http://127.0.0.1:8080/dispatch?source=official): автобус → прогноз/текущая задержка → карточка → черновик действия.
- [Аналитика](http://127.0.0.1:8080/analytics?source=official): сохранённый первый прогноз и факт для одной целевой остановки, MAE только подтверждённых пар. При пустом журнале нужно дождаться прибытия; [воспроизводимый наполненный пример](docs/25-bi-and-fleet-validation.md) содержит 229 пар и 6 неизвестных исходов.
- [Swagger Backend](http://127.0.0.1:8093/docs), [Swagger ML](http://127.0.0.1:8092/docs), [HTML PyDoc](http://127.0.0.1:8080/docs/python/).

Для первого взгляда откройте обзор: верхняя строка показывает число GPS-позиций и ТС с прогнозом, справа сразу видны проблемные ТС с прогнозом опоздания, участком и возможной причиной. Клик по событию открывает карточку ТС. При медленной или недоступной внешней картографической подложке позиции и цвета риска сначала видны на схеме по GPS; когда тайлы загружены, её заменяет обычная карта. Отсутствующий адрес остановки обозначен её ID, а не `nan`. [Снимок карты](reports/official-dashboard-current-2026-09-27.png) и [схемы без подложки](reports/official-gps-fallback-2026-09-27.png).

Во вкладке «Диспетчер» блок «Дорожные события» позволяет показать тестовое ДТП перед выбранным автобусом и отдельную рекомендацию GigaChat. Событие помечено как тестовое, а величина задержки остаётся неизвестной. Без настроенного источника живых событий интерфейс прямо сообщает, что он не подключён. Подробности и ограничения — в [описании дорожного мониторинга](docs/18-road-events.md).

Быстрые проверки: `curl -f http://127.0.0.1:8081/api/v1/health`, `curl -f http://127.0.0.1:8093/status`, `curl -f http://127.0.0.1:8092/health`. Число автобусов с прогнозом зависит от времени среза; контекстные ТС без расписания видны на карте, но не получают фиктивный прогноз. `/api/v1/ml/status` сообщает фактическую версию модели и резервный режим, если ML недоступен.

## 2. Проверка раннего предупреждения и score

Начните со [страницы завершённых эпизодов](http://127.0.0.1:8080/docs/early-warning/). Пример ТС 131672: первый сигнал **18:00**, текущая задержка **−118 с**, плановая цель **18:11**, фактическое прибытие **18:13:31**, факт доступен в срезе **18:14**. Сигнал за **11 минут** до нарушенного срока при отсутствии уже известного опоздания. Это часы официального архива, не текущие часы Москвы.

В таблице сохранены все **95** первых сигналов и их исходы. **94/94** подтверждённых нарушений срока предупреждены в окне 10–15 минут; это проверка горизонта, не полнота модели. Основная метрика риска >2 минут остаётся **92/120**, пропуски **28**, ложные сигналы **3/95**. Для повторного построения страницы сохраните JSON следующей команды в `reports/early-warning-audit-2026-09-26.json`, выполните `python3 scripts/build-warning-evidence.py` и пересоберите frontend.

Живой [журнал Backend](http://127.0.0.1:8093/warnings/audit) отдельно показывает `pending`, `awaiting_observation` и `observed`. В NDTP исход появляется только после наблюдаемого посещения целевой остановки; потеря GPS не подтверждает задержку. Плановая граница, факт прибытия и момент доступности факта — разные поля.

```sh
docker compose -f compose.official.yaml run --rm --no-deps -v "$PWD/scripts:/app/scripts:ro" backend python /app/scripts/audit-early-warnings.py
python3 -c 'import hashlib,pathlib; print(hashlib.sha256(pathlib.Path("submission/best-6-of-6.csv").read_bytes()).hexdigest())'
```

[Журнал ранних предупреждений](docs/21-early-warning-evidence.md) проверяет два независимых условия: ML-прогноз имеет цель строго `600 < план − T <= 900 с`, а первое предупреждение дополнительно выпущено за `600 < событие − T <= 900 с`. Объявленное событие — **возможное превышение опоздания на 120 с**, его отметка `event_time = план + 120 с`; фактический исход подтверждается позже. Поэтому первое предупреждение публикуется при `600 < план − T <= 780 с`, не меняя прогноз и риск на оставшейся части ML-окна. `/warnings/audit` и карточка показывают план, прогноз прибытия, отметку события и неизменное время первого выпуска; `event_lead_time_sec` относится к событию, legacy `lead_time_sec` — к плану. Фактическое прибытие оценивается отдельно: его неизвестное время не используется для выпуска сигнала. Аудит считает обнаружения, пропуски и ложные сигналы на фиксированном знаменателе и завершается ошибкой при нарушении любого временного условия.

[CSV-сабмит](submission/README.md) содержит 151 уникальную конечную строку; участник подтвердил, что именно этот файл дал 6/6 на платформе. Локальный MAE и скрытая оценка платформы — разные показатели; снимок кабинета платформы нужно приложить к сдаче отдельно.

## 3. Реальный Docker-образ эмулятора NDTP

Для проверки транспортного протокола используется **образ организаторов**, а расписание создаётся скриптом как явно учебный план на текущие минуты. Не используйте январский `schedule.csv` как текущий live-план. В том же shell, где задан `API_TOKEN`:

```sh
unzip -p ml/data/official-dataset.zip ndtp-telemetry-emulator.tar | docker load
docker run -d --rm --network transit-hub-official_default -p 127.0.0.1:18080:18080 --name transit-ndtp-emulator ndtp-telemetry-emulator:1.0
python3 scripts/prepare-ndtp-smoke.py --output docker/local-data/live --target-host backend --target-port 9201
TELEMETRY_MODE=ndtp docker compose -f compose.official.yaml up -d --no-deps --force-recreate backend
curl -f http://127.0.0.1:8093/status
curl -f -X POST http://127.0.0.1:18080/api/config -H 'Content-Type: application/json' --data-binary @docker/local-data/live/emulator-config.json
```

Через несколько секунд проверьте `curl -f http://127.0.0.1:8093/status`, `curl -f http://127.0.0.1:8093/warnings/audit`, `curl -f http://127.0.0.1:8081/api/v1/alerts` и [карту](http://127.0.0.1:8080/overview?source=official). В `/status` должны увеличиваться счётчики принятых кадров; известное устройство из `unit-map.json` даёт GPS-позицию и прогноз в плановом окне 10–15 минут. При риске опоздания первый алерт появляется только в пересечении двух окон из пункта 2; генератор создаёт первую цель через 12,5 минуты, уже внутри этого пересечения. Второе устройство в конфиге не имеет планового соответствия и не должно обрушить сервис. [Сохранённый исходный результат полного контура](reports/ndtp-emulator-smoke-2026-09-26.json) связывает кадры, Backend, API и предупреждение; он получен до уточнения окна события и подтверждает транспортную цепочку, а новое правило проверяется актуальным аудитом. План пересоздаётся перед **каждым** прогоном: окно уходит по текущим часам. Для 30-минутной проверки используйте `--target-count 10`: учебные цели будут расположены с шагом четыре минуты. Для завершения потока отправьте в `/api/config` `{"targetHost":"backend","targetPort":9201,"units":[]}`.

На реальном оценочном контуре замените учебные `schedule_plan.csv` и `unit-map.json` на действующий план и официальное соответствие устройств. Учебный генератор записывает UTC; время реального плана нужно привести к той же шкале, что и время входящих пакетов NDTP. NDTP передаёт координату/скорость/курс, а не ID остановки; сопоставление с планом выполняет сервис. Без плана либо при старом GPS прогноз остаётся недоступным.

Для проверки **наблюдённого исхода на живом бинарном потоке** запустите следующий сценарий сразу после создания плана с одной целью и запуска эмулятора. Он идёт по настоящим часам около 15 минут: сначала фиксирует первый алерт, затем подаёт через образ организаторов последовательность GPS до целевой остановки с опозданием более двух минут и проверяет неизменность первого выпуска, оба окна 10–15 минут, запас до наблюдённого прибытия и подтверждение исхода. Расписание и движение учебные; этот сценарий не измеряет MAE модели на эксплуатации.

```sh
python3 scripts/audit-live-ndtp-emulator.py \
  --plan docker/local-data/live \
  --backend http://127.0.0.1:8093 \
  --emulator http://127.0.0.1:18080 \
  --arrival-delay-sec 130 \
  --output reports/ndtp-live-window-local.json
```

Скрипт завершает передачу конфигурации эмулятора по окончании, в том числе при ошибке. Если план устарел и до цели меньше десяти минут, пересоздайте его, перезапустите Backend и повторите сценарий.

## 4. Производительность и отказоустойчивость

[Проверка запуска на Windows/Docker и найденные исправления](reports/jury-reliability-2026-09-27.md): нагрузка через Nginx, некорректные WebSocket-кадры, отключение ML/Backend и аварийный перезапуск API. Числа ниже относятся к ранее сохранённому 30-минутному прогону на другом окружении; их нельзя переносить на любую машину жюри.

[Текущий 30-минутный отчёт](reports/reliability-fleet-current-2026-09-27.json): 100 автобусов, 19,97 бинарных кадров NDTP/с, 15 читающих WS-клиентов, потеря GPS одного ТС на 210 с и реконнект TCP; P95 Backend 1,69 с, ML 0,53 с. Один из 180 срезов был честно помечен шлюзом как временно устаревший, следующий восстановился. Синтетический генератор нагрузки отделён от официального эмулятора; MAE на нём не оценивается. Команда `python3 scripts/verify-fleet-report.py reports/reliability-fleet-current-2026-09-27.json` проверяет **18 условий**, включая долю временно устаревших срезов менее 1% и восстановление. [Предыдущий прогон и BI](docs/25-bi-and-fleet-validation.md) сохранены для сравнения.

[Протокол и методика](docs/20-reliability-benchmark.md), [скрипт длительного замера](scripts/benchmark-soak.mjs), [холодный старт и контролируемые отказы](scripts/benchmark-container-lifecycle.mjs). Измеренные числа всегда привязаны к длительности, версии, машине и типу потока. Отказ ML даёт явно обозначенный резервный прогноз; потеря Backend оставляет последнее состояние со статусом устаревания. Текущая погода в интерфейсе относится к настоящему моменту и не используется для объяснения архивных задержек.
