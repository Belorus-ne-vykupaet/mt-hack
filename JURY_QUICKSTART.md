# Transit Hub — инструкция для жюри

Полный маршрут проверки: запустить Docker-контур, открыть BI, увидеть прогнозы и алерты, подать бинарный поток NDTP и проверить метрики. [Документация](DOCUMENTATION.md) объединяет PyDoc, OpenAPI/Swagger и архитектуру; [отчёт по возможностям](docs/additional-features-report.md) содержит краткие описания функций и результаты нагрузки.

## 1. Запуск ML, Backend и BI

Требования: Docker Desktop / Docker Engine с Compose, Node.js 22.9+, Python 3 и архив организаторов. Веса модели уже включены в репозиторий. Команды выполняются из корня проекта.

### macOS / Linux

```sh
git clone https://github.com/Belorus-ne-vykupaet/mt-hack.git
cd mt-hack
python3 scripts/prepare-official-data.py --save-archive ml/data/official-dataset.zip
export API_TOKEN="$(node -p "require('node:crypto').randomBytes(32).toString('hex')")"
node scripts/start-official-docker.mjs -d
docker compose -f compose.official.yaml ps
```

### Windows PowerShell

```powershell
git clone https://github.com/Belorus-ne-vykupaet/mt-hack.git
cd mt-hack
python scripts/prepare-official-data.py --save-archive ml/data/official-dataset.zip
$env:API_TOKEN = node -p "require('node:crypto').randomBytes(32).toString('hex')"
node scripts/start-official-docker.mjs -d
docker compose -f compose.official.yaml ps
```

Если ZIP уже скачан, используйте `python3 scripts/prepare-official-data.py --archive /path/dataset.zip`; для проверки эмулятора сохраните ZIP также как `ml/data/official-dataset.zip`. Docker Desktop должен работать с Linux-контейнерами.

**Результат запуска:** работают четыре сервиса `frontend`, `api`, `backend`, `ml`; `api`, `backend`, `ml` имеют статус `healthy`. Локальный ключ команд выводится скриптом запуска. При первом показе используется официальный архив: часы данных начинаются 6 января 2026 в 07:27, темп воспроизведения — 0,25.

| Что открыть | Адрес |
|---|---|
| Обзор транспортной сети | http://127.0.0.1:8080/overview?source=official |
| Аналитика | http://127.0.0.1:8080/analytics?source=official |
| Диспетчер | http://127.0.0.1:8080/dispatch?source=official |
| Единый каталог документации | http://127.0.0.1:8080/docs/ |
| Статус модели и потока | http://127.0.0.1:8081/api/v1/ml/status |
| Swagger Backend / ML | http://127.0.0.1:8093/docs · http://127.0.0.1:8092/docs |

Все адреса `127.0.0.1` открываются на компьютере с запущенным Compose. Swagger UI использует внешние web-ресурсы для интерфейса и при отсутствии интернета может не отрисоваться. В таком случае используйте локальные JSON-контракты из `public/docs/api/` и `contracts/integration-openapi.json`; для запущенного API-шлюза схема также доступна по `http://127.0.0.1:8081/api/v1/openapi.json`.

## 2. Проверка BI и прогноза за пять минут

1. Откройте **«Обзор сети»**. В верхней строке видны GPS-позиции, число автобусов с прогнозом, пунктуальность и события; карта показывает транспорт и линии маршрутов.
2. Нажмите событие справа. В карточке проверьте автобус, целевую остановку, текущую задержку, прогноз, вероятность риска и участок. Время первого сигнала и наблюдаемый фактор позволяют разобрать конкретную ситуацию.
3. Переместите нижний ползунок от **0 до 15 минут**: положение автобусов обновляется во время перетаскивания. Переключите карту в **3D**, выберите автобус и смените светлую/тёмную тему.
4. Откройте **«Аналитику»**. Проверьте динамику задержек, распределение риска, рейтинг маршрутов и блок **«Факт и сохранённый прогноз»**. Первый прогноз сохраняется; после наблюдаемого прибытия появляются факт и ошибка, а MAE рассчитывается по подтверждённым парам.
5. Откройте **«Диспетчер»**, выберите автобус и подсказку. Кнопка подстановки заполняет форму; сохранение решения пишет команду в серверный журнал. Для операций записи используйте ключ, выданный при запуске; вход доступен по адресу `/integrations`.

**Проверка модели:** `/api/v1/ml/status` показывает `modelVersion: olya-extra-trees-osm-v1`, 64 признака и сохранённые метрики модели. `/api/v1/forecast` содержит прогнозы транспорта и участки; `/api/v1/alerts` — события текущего среза.

## 3. Проверка временного окна и наблюдённых исходов

Откройте [страницу ранних предупреждений](http://127.0.0.1:8080/docs/early-warning/): она показывает сохранённые эпизоды «первый сигнал → план → наблюдённое прибытие». Это воспроизводимый архивный аудит; интерактивный поток проверяется отдельно через `/warnings/audit` Backend.

Логика первого сигнала проверяет две отметки: до плановой остановки `600 < план − T <= 900 с`, до события превышения опоздания на 120 с `600 < план + 120 − T <= 900 с`. Первое предупреждение сохраняет время выпуска; последующие GPS-наблюдения подтверждают исход и не переписывают исходный прогноз.

В [сохранённом прогоне официального эмулятора с активной OSM-моделью](reports/ndtp-live-window-osm-2026-09-27.json) первый сигнал выпущен за **691,4 с до плана**, **811,4 с до порога** и **821,4 с до наблюдённого прибытия**; наблюдённое опоздание — **130 с**. При этом на предыдущей остановке уже было опоздание. Архивный аудит той же модели содержит **7 подтверждённых предупреждений без уже наблюдаемого опоздания**. Отдельный живой сценарий с предыдущей остановкой на 30 с впереди времени создания плана прошёл через NDTP и ML, но предупреждения не дал; [результат и наблюдения](reports/ndtp-live-on-time-osm-2026-09-27.json). Формулы, полный набор исходов и команды повторения приведены в [методике](docs/21-early-warning-evidence.md).

## 4. Подача потока из официального NDTP-эмулятора

Проверка использует Docker-образ организаторов и интеграционный план, созданный на текущие минуты. Это позволяет воспроизвести связку **NDTP → Backend → ML → API → BI** с известными входными данными. Выполняйте в том же терминале, где задан `API_TOKEN`, после запуска основного контура.

Извлеките образ из сохранённого архива и загрузите его:

```sh
python3 -c "import zipfile; z=zipfile.ZipFile('ml/data/official-dataset.zip'); z.extract('ndtp-telemetry-emulator.tar', 'docker/local-data')"
docker load -i docker/local-data/ndtp-telemetry-emulator.tar
docker run -d --rm --network transit-hub-official_default -p 127.0.0.1:18080:18080 --name transit-ndtp-emulator ndtp-telemetry-emulator:1.0
python3 scripts/prepare-ndtp-smoke.py --output docker/local-data/live --target-host backend --target-port 9201
```

Переключите Backend на этот поток, затем обновите каталог API:

```sh
TELEMETRY_MODE=ndtp docker compose -f compose.official.yaml up -d --no-deps --force-recreate --wait backend
docker compose -f compose.official.yaml up -d --no-deps --force-recreate --wait api
curl -f -X POST http://127.0.0.1:18080/api/config -H 'Content-Type: application/json' --data-binary @docker/local-data/live/emulator-config.json
```

В PowerShell используйте `python` вместо `python3`, `$env:TELEMETRY_MODE = 'ndtp'` перед командой Compose и `curl.exe` вместо `curl`.

**Что проверить:**

- `http://127.0.0.1:8093/status`: растёт `ndtp.frames`, известные устройства учитываются в `mappedPackets`, появляется `predictedVehicles`.
- `http://127.0.0.1:8093/snapshot`: координаты, `forecast_status`, целевая остановка, `predicted_delay_sec`, `risk_probability`.
- `http://127.0.0.1:8093/warnings/audit`: время первого предупреждения и окна до плана/события для обнаруженного риска.
- `http://127.0.0.1:8081/api/v1/alerts` и обзор сети: соответствующий автобус и его событие.

Первая цель плана создаётся через 12,5 минуты; перед новым прогоном повторите подготовку плана и перезапуск Backend/API. Для последовательности целей на полчаса добавьте `--target-count 10`.

Для проверки первого предупреждения и последующего прибытия на настоящих часах создайте свежий план с одной целью, затем запустите:

```sh
python3 scripts/audit-live-ndtp-emulator.py --plan docker/local-data/live --backend http://127.0.0.1:8093 --emulator http://127.0.0.1:18080 --arrival-delay-sec 130 --output reports/ndtp-live-window-local.json
```

Сценарий занимает около 15 минут, сохраняет JSON и завершает передачу по окончании. Состав интеграционного плана и движения обозначен в результате проверки. Для потока оператора входом служат предоставленные им действующий `schedule_plan.csv` и mapping `unit-map.json`; [формат, сверка ID и временной зоны](DOCUMENTATION.md#входные-данные-ndtp), [порядок получения и подключения](docs/27-live-ndtp-plan-source.md).

Возврат к официальному архиву:

```sh
docker stop transit-ndtp-emulator
TELEMETRY_MODE=replay docker compose -f compose.official.yaml up -d --no-deps --force-recreate --wait backend
docker compose -f compose.official.yaml up -d --no-deps --force-recreate --wait api
```

В PowerShell перед возвратом задайте `$env:TELEMETRY_MODE = 'replay'`.

## 5. Дополнительные возможности

| Возможность | Как показать |
|---|---|
| Яндекс Погода | Включить погодный слой в 3D; при осадках появляются облака и анимированный дождь |
| Дорожные события | В диспетчерской выбрать автобус и показать «Тестовое ДТП»: событие впереди по маршруту, анализ GigaChat, статус «Задержка не определена» |
| Подсказки GigaChat | Открыть рекомендации выбранного автобуса, затем подставить действие в форму |
| Отчёты GigaChat | Открыть «Отчёты», сформировать текст по сохранённой сводке и переключить дату |
| Исторический OpenStreetMap | Проверить версию модели, 64 признака и 14 OSM-признаков в `/api/v1/ml/status` |
| Прогнозный ползунок | Перетащить 0–15 минут вперёд и назад в 2D и 3D |
| ПК и Android | Кнопки установки PWA и скачивания APK в интерфейсе |
| 3D-карта | Объёмные автобусы, направление движения, выбор транспорта, погодные слои |

Для Яндекс Погоды и GigaChat задайте свои серверные ключи перед запуском либо в локальном `server/.env`; полный список настроек — в [документации](DOCUMENTATION.md#интеграции-и-настройки). Адаптер Яндекс Router и дорожной ленты принимает отдельные ключи/URL; сценарий «Тестовое ДТП» доступен для показа дорожной логики. Краткие комментарии по каждой функции и её проверке — в [общем отчёте](docs/additional-features-report.md).

## 6. Производительность и автоматические проверки

Текущая версия прошла **155 тестов приложения/API, 149 Python-тестов и полный набор из 15 браузерных сценариев** на архивном Docker-стенде; пропусков и повторных попыток браузерных тестов нет. [Финальный протокол](docs/29-final-criteria-verification.md) содержит команды, версию модели и новый снимок дашборда.

В сохранённом 60-секундном Docker-прогоне: 100 тестовых автобусов, 25 постоянных WS-клиентов, 1550 HTTP-запросов без ошибок, 0 неожиданных разрывов, P95 HTTP 550,25 мс; отдельная проверка перезапуска API — 7,10 с. **30-минутный прогон активной OSM-модели на 100 ТС и 15 WS-клиентах завершился успешно на другом компьютере по подтверждению участника.** Его JSON ещё не передан в репозиторий, поэтому конкретные перцентили этого прогона здесь не заявляются; опубликованные числа относятся к сохранённым отчётам. [Все показатели и исходные отчёты](docs/additional-features-report.md#измеренные-показатели).

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm ml:test
OFFICIAL_BASE_URL=http://127.0.0.1:8080 pnpm exec playwright test --config playwright.official.config.ts
```

Для `pnpm ml:test` подготовьте Python-окружение по [ML README](ml/README.md). Для браузерного прогона используется Chrome. В PowerShell переменные задаются через `$env:ИМЯ = 'значение'`; Python-проверки можно запустить напрямую через установленный интерпретатор с `PYTHONPATH`, содержащим `ml` и `src`.

Повторение нагрузочного сценария, параметры 100 ТС / 25 клиентов, тест перезапуска и JSON-результаты — в [протоколе проверки](docs/28-karatai-reliability-review.md#как-повторить). Контейнеры автоматически перезапускаются после сбоя; логи ограничены тремя файлами по 10 МБ на сервис, данные журналов сохраняются в Docker-томах.
