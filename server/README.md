# API-сервис для демонстрации интеграции

Это запускаемый **учебный сервер**, а не NDTP-эмулятор организаторов или подключение к перевозчику. Он выдаёт наши синтетические CSV через настоящий HTTP/WebSocket, принимает решения диспетчера и применяет их к серверной копии демонстрации. Рекомендации пока работают по правилам. Система не выдаёт демонстрационные ответы за производственные данные.

## Локальный показ жюри

Node.js 22.13+ / pnpm, из корня репозитория:

```sh
pnpm install --frozen-lockfile
pnpm demo
```

Запускаются API на `127.0.0.1:8081` и собранный сайт на `127.0.0.1:4173`. Порты должны быть свободны. Откройте `/integrations`, проверьте связь и нажмите **«Подключить сайт к API»**. Переключение сохраняется только в текущей вкладке. Заголовок меняется на `API`; MSW в этом режиме не запускается.

Показ: «Интеграции» → сервер доступен → «Диспетчер» → подставить предложение → **«Отправить по API»** → сервер подтвердил → количество автобусов на карте изменилось → перезагрузить страницу → журнал сохранён → отменить → сеть восстановилась.

Можно запускать отдельно: `pnpm api:serve` и `pnpm dev`. Vite проксирует `/api/v1` и WebSocket на сервер; `/integration/v1` — отдельный путь для проверки API из локального mock-режима. При другом порте сервера задайте серверную переменную `API_PROXY_TARGET` перед запуском Vite. Не используйте wildcard CORS. Страницы API и mock доступны параллельно в разных вкладках; их журналы разделены.

## Общий тестовый ключ погоды

По запросу владельца в репозиторий добавлен `server/weather-demo.env` с тестовым ключом Яндекс Погоды. `pnpm demo`, `pnpm api:serve`, `pnpm hackathon` и `pnpm docker:official` загружают его автоматически: участникам достаточно обновить проект и запустить его. Ключ действует до 2 октября 2026 года; лимит 10 000 общий, каждый отдельный сервер имеет свой кэш и расходует квоту.

Переменные окружения процесса имеют высший приоритет, затем `server/.env`, затем общий тестовый файл. Для личного ключа задайте `YANDEX_WEATHER_KEY` в `server/.env`; пустое значение в нём отключает общий ключ. Остальные секреты остаются только в игнорируемом `server/.env`. Тестовый ключ не включается в браузерную сборку и не копируется в Docker-образ: контейнер получает его только при локальном запуске. **Перед публикацией репозитория отзовите его в кабинете Яндекса: удаление файла не удаляет ключ из истории Git.** Для постоянного использования нужен личный ключ или общий сервер.

## Автобусы, черновики водителям и GigaChat

На странице «Диспетчер» вместо графика по выбранному маршруту показаны все автобусы потока, их текущая задержка и прогноз к целевой остановке. Отсутствующий прогноз обозначается прочерком. Кнопки «Написать», «Скорость» и «Стоянка» готовят адресный черновик; сервер проверяет маршрут, автобус, остановку и диапазоны значений, сохраняет его в `DRIVER_OUTBOX` (`server/data/driver-messages.json` по умолчанию) и возвращает статус **draft**. Реальный канал доставки водителям пока не подключён: черновик не выдаётся за отправленную команду. В Docker журнал находится в существующем томе `dispatch-journal`. Чтение и создание черновиков требуют авторизации, в том числе при `API_PUBLIC_READ=true`.

Панель помощника сразу показывает явно помеченные подсказки по правилам. `GET /api/v1/dispatch/advice?route_id=…` не вызывает внешнюю модель. Для анализа GigaChat добавьте в игнорируемый `server/.env` строку `GIGACHAT_AUTH_KEY=...` (ключ авторизации Base64 из кабинета, без префикса `Basic`) и перезапустите сервер. По умолчанию используется `GigaChat-3-Ultra` с `GIGACHAT_SCOPE=GIGACHAT_API_PERS`; модель можно переопределить через `GIGACHAT_MODEL`. При запуске `pnpm docker:official` скрипт также передаёт ключ в API-контейнер через окружение; ключ не попадает в браузерный код и Docker-образ. Проверка TLS включена, дополнительный [корневой сертификат](certs/README.md) загружается только сервером. Кнопка «Спросить GigaChat» отправляет ограниченную сводку выбранного **архивного** маршрута: задержки, прогнозы, скорость, следующую остановку и резерв. Токен OAuth кэшируется до истечения срока. Ответ модели проверяется по количеству задержанных автобусов, их доле, типам действий и существующим ID; при неверном расчёте интерфейс остаётся на проверенных правилах. Рекомендация модели остаётся гипотезой для оператора. Автоматической отправки водителям и гарантированной оценки эффекта нет. [Схема OAuth и новый API GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api).

Страница «Отчёты» показывает краткую сводку последней даты и вкладку сохранённых дней. Сервер раз в минуту **времени потока** фиксирует агрегаты, а не перечитывает большой CSV при открытии страницы. Срезы и созданные тексты GigaChat хранятся в `DAILY_REPORT_STORE` (`server/data/daily-reports.json` по умолчанию; в Docker — существующий том). `GET /api/v1/dispatch/reports` и `GET /api/v1/dispatch/reports/{date}` не вызывают модель; `POST /api/v1/dispatch/reports/{date}/generate` по действию оператора формирует и сохраняет короткий текст через Ultra. Числовые показатели рассчитывает сервер. Интервал наблюдений и число срезов указаны в каждом отчёте: отсутствие данных за часть дня не подменяется выдуманным итогом.

## Контракт

Полный OpenAPI: `contracts/integration-openapi.json`, доступен через `GET /api/v1/openapi.json`. Исходный `contracts/openapi.json` сохранён для сгенерированного сетевого клиента. Дополнительный клиент диспетчера находится в `src/shared/api/integrations.ts`.

| Метод / путь после `/api/v1` | Назначение |
|---|---|
| GET `/health`, `/integrations` | Состояние API, источников и модели, без секретов |
| GET `/routes`, `/vehicles`, `/alerts`, `/network/summary` | Сеть из CSV; также поддержаны geometry, forecast и analytics существующего frontend-контракта |
| WS `/stream` | События сети и heartbeat, последовательность отдельно для каждого клиента |
| GET `/dispatch/recommendations` | Правила на сервере, время выпуска/истечения, revision и резерв |
| GET `/dispatch/commands` | Серверный журнал и revision |
| POST `/dispatch/commands` | `{plan, mode: "plan" / "apply", revision}`, обязательный `Idempotency-Key` |
| POST `/dispatch/commands/{id}/cancel` | `{revision}`, отмена плана или демоприменения |
| POST `/session` | `{token}` → HttpOnly SameSite=Strict cookie |
| GET `/external/weather` | Живая погода Москвы, кэш 15 минут |
| GET `/external/traffic?route_id=...` | Дорожный проезд между первыми остановками, кэш 2 минуты |

Пример тела команды (ID маршрута и остановки нужно получить из `/routes`):

```json
{
  "revision": 0,
  "mode": "apply",
  "plan": {
    "routeId": "м3",
    "stopId": "ID_ИЗ_API",
    "baseFleet": 8,
    "targetFleet": 9,
    "cycleMin": 120,
    "baseDwellSec": 30,
    "targetDwellSec": 20
  }
}
```

Ответ содержит новый журнал, свободный резерв и revision. Жизненный цикл учебного исполнителя: `accepted → applied_demo`, затем `cancelled` или `replaced`; сохранённый без применения план имеет статус `draft`. Название `applied_demo` намеренно не означает подтверждение городского диспетчерского сервиса. На реальном исполнителе потребуются отдельные `requested/accepted/executed/rejected`, серверные полномочия и подтверждения перевозчика.

Повтор идентичного запроса с тем же ключом не применяет действие дважды. Повтор ключа с другим телом и устаревшая revision возвращают 409. Резерв общий и проверяется на сервере. Неизвестные остановки, недопустимые числа и стоянка ниже 20 секунд для учебного применения отклоняются. 20 секунд — правило демо, не норматив. Отмена тоже проверяет revision. Файл журнала сохраняется атомарно; ошибки записи не меняют состояние в памяти.

Журнал: `server/data/commands.json`, в git не попадает. Для сброса остановите сервис и переместите файл в архив. В текущей реализации только **один процесс** пишет журнал; для нескольких инстансов нужна база данных с транзакциями, уникальным ключом идемпотентности и блокировкой ресурса. Журнал ограничен 5000 командами, затем требуется архивирование. Это reference API для интеграции, не готовая высоконагруженная диспетчерская.

## Настройка ключей и доступа

Скопируйте `server/.env.example` в `server/.env`. Сервер читает его сам. Не кладите ключи в `VITE_*` или CSV. По умолчанию он слушает только loopback. При публикации на другом интерфейсе обязательны `API_TOKEN` (24+ URL-safe символа) и список `API_ORIGINS`. В браузере ключ вводится на странице «Интеграции», в bundle/localStorage он не записывается. CLI-клиент может использовать `Authorization: Bearer ...`. Для внешнего доступа добавьте TLS/SSO, роли пользователей, аудит личности и ограничения частоты; текущий общий ключ предназначен для стенда.

`VITE_API_URL` — адрес общего API, `VITE_WS_URL` — поток (пустое значение использует тот же origin), `VITE_INTEGRATION_URL` — необязательный отдельный gateway. Если существующий backend пока предоставляет только чтение сети, задайте `VITE_DISPATCH_API=false`. Рекомендуемый вариант — единый origin через reverse proxy, чтобы cookie и WebSocket использовали одну сессию.

## Погода и трафик

Отдельный [3D-слой текущей погоды Яндекс](../docs/17-yandex-weather-layer.md) подключается через `YANDEX_WEATHER_KEY`. Использует доступные на тестовом тарифе данные 13 точек Москвы, общий кэш 15 минут и условные погодные формы. Кнопка «Погода» находится у переключателя 2D/3D. Отказ источника и неполные данные показываются явно. Точечный режим не обращается к Nowcast; адаптер точных тайлов сохранён для будущего подключения.

- Погода: [Open-Meteo](https://open-meteo.com/en/docs), текущая температура/осадки в центре Москвы, UTC и время получения. Запрос выполняется по кнопке; ошибки не подменяются придуманными данными.
- Диспетчерская показывает отдельную сводку текущей Яндекс Погоды по 13 точкам Москвы и ведёт на 3D-карту. Если подключён GigaChat, его запрос получает эту сводку отдельно от архивной телеметрии. Текущая погода не используется как причина архивных задержек или признак для их прогноза.
- Трафик: [Яндекс Router API](https://yandex.ru/maps-api/docs/router-api/request.html), `YANDEX_ROUTER_KEY` только на сервере. Два запроса: с трафиком и `traffic=disabled`. Длительность суммируется по шагам [ответа API](https://yandex.ru/maps-api/docs/router-api/response.html). Если геометрии ответов различаются, коэффициент не вычисляется. Даже одинаковые автомобильные пути ещё надо сопоставить с автобусной геометрией и полосами.
- Таймаут каждого запроса 6 секунд, общие кэш и объединение одинаковых одновременных запросов. Недоступный провайдер даёт явную ошибку; ключ и сырые ошибки с URL не возвращаются клиенту. Нет автоматических платных запросов при каждом кадре карты.
- Живые внешние данные **не включаются в признаки исторического CSV**. Они показаны отдельно для демонстрации подключения. `usedInModel: false`. Перед включением нужна согласованность времени, географии и проверка MAE, описанная в документах 15/16.
- Ключ Яндекс Router API не предоставлен: сетевой запрос к нему не подтверждён. Обработка ответа и ошибок проверяется фикстурами. Тестовый ключ Яндекс Погоды проверен: обычный прогноз доступен, права на Nowcast отклонены. Для реального использования проверьте договор, квоты и права хранения.

## Подключение ML-команды

Задайте `ML_SERVICE_URL` — полный адрес POST endpoint (например, `http://127.0.0.1:8000/predict`), при необходимости `ML_SERVICE_TOKEN`. Сервер отправит:

```json
{"schemaVersion":1,"asOf":"2026-09-23T07:15:00.000Z","horizonSec":900,"vehicles":["VehicleDto из контракта, реальные объекты"],"externalContext":null}
```

Ответ должен содержать **все** переданные автобусы ровно один раз:

```json
{"asOf":"2026-09-23T07:15:00.000Z","modelVersion":"team-model-v1","predictions":[{"vehicleId":"vehicle-742","delaySec":240}]}
```

В примере показана одна запись; фактический массив должен покрывать весь запрос. `asOf` обязан совпасть, задержка — конечное число в диапазоне −3600…86400 секунд. Проверяются неизвестные/повторные ID, полнота, время и числа. Таймаут 2,5 секунды; при отказе/ошибке остаётся persistence baseline, статус подключения явно `fallback`. Вывод модели кэшируется на временной срез телеметрии. Обученная модель не входит в этот репозиторий; подключение проверено тестовым ответом, качество MAE не заявляется.

Это интеграция **прогнозов**, а не причинной оценки действий. Рекомендации остаются правилами, теперь используют прогноз от подключённого сервиса. `predictedDelayAfterActionSec` остаётся null. Ввод NDTP подключается отдельным адаптером вместо CSV-источника; формат официального эмулятора ещё неизвестен, его поддержку не имитируем.

## Docker

```sh
export API_TOKEN="$(openssl rand -hex 24)"
docker compose -f compose.yaml -f compose.api.yaml up --build
```

Сайт на `localhost:8080`, API доступен через него, порт сервера наружу не публикуется. Журнал в Docker volume. Введите свой API_TOKEN на странице «Интеграции». Для реальной публикации нужен TLS. Синтаксис Compose проверен. Контейнерная сборка в этой среде не выполнялась: Docker daemon не запущен. Локальный Node-сервис и браузерный сценарий проверены.

## Проверки

`pnpm check` включает типы frontend/backend, lint, модульные/HTTP/WS тесты и сборку. `PLAYWRIGHT_CHANNEL=chrome pnpm test:api` запускает отдельные сервер и сайт и проверяет REST/WS, серверные рекомендации, отправку, перезагрузку, отмену, отсутствие подключения и мобильную страницу. Тесты внешних провайдеров детерминированы и не требуют ключей.
