# Проверка запуска для жюри · 27 сентября 2026

Проверяемая база: `d5c6158` (`origin/main`, обновление на 34 коммита). Исправления этой проверки находятся поверх неё. Хост: Windows x64, Docker Desktop/WSL2, Linux-контейнеры, Node 22.14 на хосте. Запуск: `node scripts/start-official-docker.mjs -d` / `compose.official.yaml`; сайт и тесты идут через Nginx на `127.0.0.1:8080`, четыре сервиса frontend/API/Backend/ML. Модель: `sasha-extra-trees-v2`.

## Исправленные проблемы

- Исходный API завершался с кодом 1 после одного входящего WebSocket-кадра 65 537 байт: необработанный `WS_ERR_UNSUPPORTED_MESSAGE_LENGTH`. Воспроизведено отдельным процессом исходного `server/app.ts`. Теперь ошибка закрывает только соединение; проверено регрессионным тестом и через Nginx под нагрузкой.
- Некорректный URL при HTTP Upgrade мог вызвать необработанное исключение вне HTTP-обработчика. Теперь возвращается 400; регрессионный тест проверяет доступность API после запроса.
- `pnpm api:serve` не запускался на Windows из-за POSIX-синтаксиса переменной окружения. Переносимый `scripts/start-api.mjs` задаёт сертификат перед запуском Node.
- Добавлены `restart: unless-stopped` и ротация Docker-журналов: 3 × 10 МБ на сервис. Явно остановленные контейнеры остаются остановленными.
- Таймаут диагностического скрипта восстановления увеличен с 2,5 до 5 секунд: он должен дождаться ответа шлюза, чей upstream timeout — 3,5 секунды. На Windows остановленный Docker-сервис может молча отбрасывать пакеты вместо немедленного connection refused.
- На 100 ТС обнаружена блокировка чтений за ML-пересчётом: за исходный пятиминутный прогон — 19 замеров с HTTP-ошибками и 30 устаревших статусов. Backend теперь отдаёт последний полный снимок во время расчёта, уступает цикл событий между ТС и публикует статус модели вместе с новым снимком. Потеря GPS продолжает обновлять свежесть по запросу даже без новых пакетов. Регрессионный тест удерживает ML-ответ и проверяет 20 HTTP-чтений до его завершения: исходная версия зависает, исправленная проходит.
- Таймаут ответа ML увеличен до ограниченных 3,5 с (соединение — 1,5 с): он включает разбор/валидацию истории всего парка, а не только время модели. Исходные 1,5 с вызывали `ReadTimeout` на 100 ТС.
- Генератор нагрузочного CSV явно использует UTF-8: системная кодировка Windows на этой машине — cp1251, несовместимая с Linux-чтением CSV по умолчанию.
- Отправка большого WS-пакета больше не ограничивается общими 3 секундами при продолжающейся передаче: таймаут одного кадра — 3 с, всего пакета — 30 с. Очередь по-прежнему ограничена 1 МБ; зависшие клиенты отключаются. Добавлен тест поступательного приёма, который не проходил с прежним общим дедлайном.
- Сбор Docker RSS в нагрузочном клиенте стал асинхронным, чтобы сам измеритель не блокировал чтение WebSocket во время восьми Docker-команд. Коды и причины неожиданных закрытий теперь включаются в JSON.

## Усиленная проверка 100 ТС

Это отдельный синтетический NDTP-генератор, 20 кадров/с, прогрев 30 минут истории, 15 читающих WS-клиентов. GPS одного ТС отключается на 210 секунд, TCP переподключается на 150-й секунде. Точность модели на искусственных маршрутах не оценивается.

- Исходный прогон: `jury-fleet-100-before-2026-09-27.json` — 19 диагностических срезов с HTTP-ошибками, 30 устаревших срезов.
- После изменения Backend: `jury-fleet-100-2026-09-27.json` — 1 срез с ошибками прямых диагностических запросов, 0 устаревших срезов; 15 обрывов WS. Этот промежуточный результат не считается успешным. Причина закрытия ещё не записывалась, поэтому нельзя строго приписать все обрывы одной причине; затем исправлены общий дедлайн WS и блокировка измерителя при сборе RSS.
- Итог: `jury-fleet-100-verified-2026-09-27.json`, 304 секунды, неизменные исходники во время измерения. Все 100 ТС дошли до клиентов; 86 040 сообщений, 3 900 heartbeat, **0 обрывов/ошибок WS, 0 ошибок/неизвестных кадров NDTP, 0 устаревших статусов шлюза**. Во всех 61 срезе Backend `connected`; после восстановления GPS снова доступны прогнозы всех 100 ТС.
- **Остался один таймаут первого запроса `/api/v1/forecast`**, до 4 секунд, в начале подключения клиентов. Остальные 60 замеров прошли: P95 HTTP 2 246 мс. Общий пересчёт P95 **8 222 мс**, ML P95 **1 771 мс**; задержка от GPS-времени до сообщения клиенту P95 **16 075 мс**. Пик RSS: API 643,9 МБ, Backend 207,6 МБ, ML 374,8 МБ.

Итоговый тест подтвердил устойчивость соединений и восстановления, но **не подтверждает прежнюю заявленную производительность 100 ТС / P95 < 2 с на этой Windows/WSL-машине**. Он короче 30 минут и не проходит все условия `verify-fleet-report.py`; такой результат нельзя объявлять полным прохождением старого нагрузочного критерия. Для жюри здесь оставлен штатный архивный режим, на котором смешанная нагрузка прошла без ошибок. Нагрузочные тесты архивного режима и восстановление сервисов в таблице выше выполнены до последних изменений Backend/WS; финальные функциональные проверки приведены отдельно ниже.

## Окружение и границы выводов

Первую сборку блокировали старый служебный сокет Docker, затем заполнение C: и повреждённые кэши. По разрешению пользователя хранилище перенесено в `D:\transit-jury-docker\wsl`, резервная копия настройки — `D:\transit-jury-docker\settings-store.before.json`. Повреждённый кэш зависимостей и тестовый образ эмулятора загружены заново. Также был один сетевой TLS-timeout Docker Hub. Эти сбои нельзя выдавать за падения приложения под нагрузкой.

Проверка относится к этой машине, локальной сети и указанной нагрузке. Три минуты измерения памяти не доказывают отсутствие многочасовых утечек. Холодный запуск измеряет старт готовых образов, без скачивания и сборки. Среда с меньшим объёмом памяти/CPU или более высокой нагрузкой требует отдельного замера. Стопроцентная гарантия отсутствия любых падений невозможна.
