# Подготовка CSV к хакатону

Это **предполагаемый промежуточный формат**, не контракт организаторов. CSV синтетические: расписания и задержки придуманы; геометрия и остановки — OSM (атрибуция в `src/data/README.md`). В комплекте 15 автобусных направлений, 120 рейсов, 4248 строк расписания, 3720 сообщений за 30 минут, 458 остановок и 7895 точек дорог.

## Быстро проверить и посмотреть

Из корня проекта:

```sh
pnpm data:check
pnpm data:import
VITE_MOCK_SCENARIO=csv pnpm dev --host 127.0.0.1
```

Откройте `/overview` по адресу, который напечатает сервер. Для собранного сайта:

```sh
VITE_MOCK_SCENARIO=csv pnpm build
pnpm preview --host 127.0.0.1 --port 4173
```

Вернуться к анимированной демонстрации: обычный `pnpm dev` / `pnpm build` без этой переменной. Если переменная задана в `.env.local`, удалите её или установите `VITE_MOCK_SCENARIO=route-primary-delay`.

В режиме CSV сайт показывает архив по времени событий, от первого сообщения к последнему, без заглядывания в будущие строки. На конце архива фиксируется последний срез. Пропавший на 3 минуты автобус исключается из активных. Прогноз — прозрачный базовый вариант: текущая задержка сохранится. Вероятность не придумана, проценты риска скрыты. Цвет отражает пороги задержки интерфейса, а не официальные критерии хакатона. Геометрия без измерений по участкам остаётся без выдуманных заторов. CSV не заменяет онлайн-подключение эмулятора и обученную модель.

## Файлы

| Файл | Одна строка | Обязательные поля промежуточного формата |
|---|---|---|
| `example/routes.csv` | Направление маршрута | route_id, route_number, route_name |
| `example/stops.csv` | Остановка | stop_id, stop_name, lat, lon |
| `example/schedule.csv` | Остановка конкретного рейса | trip_id, vehicle_id, route_id, stop_id, stop_sequence, arrival_time, departure_time |
| `example/telemetry.csv` | Сообщение автобуса | timestamp, trip_id, vehicle_id, lat, lon, speed, delay, next_stop_id |
| `example/shapes.csv` | Точка дорожной геометрии | route_id, point_sequence, lat, lon |

Все ID — строки, ведущие нули сохраняются. Координаты — WGS84; lat и lon явно разнесены. Задержка со знаком: отрицательная означает опережение. Время — ISO 8601 с датой и часовым поясом, например `2026-09-23T10:00:00+03:00`; полночь указывается реальной следующей датой. Стоянка вычисляется как разность departure_time и arrival_time. Геометрия содержит дорожные точки, не прямые линии между остановками.

## Когда придут данные организаторов

1. Положите файлы в отдельную папку, например `admin/csv/official/` (не публикуйте без проверки правил).
2. Скопируйте `profiles/default.json` в профиль организаторов.
3. В каждом `tables.<имя>.file` задайте имя входного файла. Справа в `columns` укажите его реальные заголовки. Слева остаются имена промежуточного формата:

```json
"telemetry": {
  "file": "ndtp_history.csv",
  "delimiter": ";",
  "columns": {
    "timestamp": "event_time",
    "trip_id": "journey",
    "vehicle_id": "bus_number",
    "lat": "latitude",
    "lon": "longitude",
    "speed": "velocity",
    "delay": "deviation",
    "next_stop_id": "next_station"
  }
}
```

4. Настройте `units.speed`: `kmh` / `mps`; `units.delay`: `seconds` / `minutes`; `decimal`: `.` / `,`; разделитель `,`, `;` или `\t`. `encoding` поддерживает UTF-8 (с BOM и без) и UTF-16LE средствами Node. Windows-1251 сначала перекодировать в UTF-8.
5. `time.schedule` и `time.telemetry`: `iso`, `local` (`YYYY-MM-DD HH:mm:ss`), `unix_s`, `unix_ms`. Для `local` задайте `time.utcOffset`, например `+03:00`. Это фиксированный offset, не календарь смены DST.
6. Проверьте и импортируйте:

```sh
pnpm data:check --dir admin/csv/official --profile admin/csv/profiles/organizers.json
pnpm data:import --dir admin/csv/official --profile admin/csv/profiles/organizers.json
```

`--check` не пишет файлы. Успешный импорт атомарно заменяет `src/data/imported-feed.json`; при ошибке предыдущая версия сохраняется. `--out` позволяет проверить результат в другом месте. После импорта пересоберите сайт с режимом CSV. Редактора или загрузки файлов для посетителей сайта нет: это инструмент администратора репозитория.

Если в файлах тот же смысл полей, достаточно изменить профиль. Если будут только часы без даты, другая система координат, отсутствующие trip_id/next_stop_id, отдельные назначения автобусов или иной смысл задержки, понадобится дополнительный адаптер. Нельзя обещать совместимость одним переименованием до публикации схемы. `route_id` должен различать направления/варианты маршрута; один номер для обоих направлений требует нормализации. Сейчас импорт отклоняет различные последовательности остановок под одним route_id, не смешивает их молча.

## Проверенный альтернативный профиль

`example/telemetry-ru.csv` содержит те же сообщения с русскими заголовками, `;`, десятичной запятой, Unix milliseconds, м/с и минутами. Остальные таблицы общие:

```sh
pnpm data:check --profile admin/csv/profiles/russian.json
pnpm data:import --profile admin/csv/profiles/russian.json --out /tmp/transit-feed-ru.json
```

Модульные тесты сравнивают оба результата. Дополнительно проверяются кавычки и переносы строк, ведущие нули, некорректные заголовки, неизвестные ID, дубликаты сообщений, единицы и время, последовательность остановок, отсутствие будущих данных в прогнозе. Данные можно воспроизвести: `python3 scripts/generate-csv.py`, затем `pnpm data:import`.

## Границы MVP

Импорт целиком выполняется в памяти. Для больших исторических архивов нужен потоковый backend; не включайте гигабайты телеметрии в frontend-сборку. Импортированный JSON попадает в браузер — публикуйте только разрешённые данные. Для реального эмулятора используйте отдельный адаптер → существующие REST/WS-контракты. Планировщик на CSV может сохранить план, но не переписывает архивные факты.
