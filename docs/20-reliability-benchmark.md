# Производительность и устойчивость локального контура

Официальное условие, критерий 5 (0–4 балла): низкая задержка инференса (ориентир <1–2 с), обработка потока без роста очередей, сохранение последнего состояния при обрыве связи и восстановление после реконнекта. Документ фиксирует воспроизводимую проверку; балл назначает жюри.

## Что происходит при обрыве

Python Backend кэширует один снимок не менее секунды; Node-шлюз объединяет одновременные запросы к нему. Когда Python Backend перестаёт отвечать, шлюз сразу отдаёт последний полный снимок. Он сохраняет исходный `timestamp` и передаёт через WebSocket `stale: true`, поэтому интерфейс пишет «Данные устарели», даже если продолжает получать события из кэша. Неудачные повторы ограничены интервалами 1, 2, 4, 8 и 15 секунд. После успешного ответа данные и статус обновляются автоматически. Неполный JSON не замещает исправный снимок. Если сервис ещё ни разу не ответил, шлюз честно возвращает ошибку, а во время паузы повторов не создаёт новые запросы к нему.

При отказе только ML-ядра Python Backend сохраняет позицию и текущую задержку, переключается на явно обозначенный persistence fallback и не выдаёт фиктивную вероятность задержки. Это иной сценарий, чем потеря Python Backend целиком.

## Поток при нескольких вкладках

До исправления WebSocket каждый тик отправлял все остановки каждого маршрута в отдельных `route.updated` и затем повторял их массивом в `forecast.updated`. На измеренном срезе было 21 активное маршрутное задание с 5475 плановыми остановками: `JSON.stringify` одних полных `route.updated` занимал 725 338 байт на тик, а повторный массив маршрутов — ещё 725 360 байт. При 15 вкладках это около 21,8 МБ сериализуемых данных каждую секунду, даже если маршруты не менялись. У медленного клиента очередь WebSocket росла без предела; локальный Node-процесс действительно дважды достигал лимита кучи около 4 ГБ за несколько минут.

Теперь полный маршрут со списком остановок отправляется только при его появлении. Дальнейшие тики передают лишь действительно изменившиеся задержки, риски и выпуск компактными патчами: даже если изменились все 21 активное задание, это около 3664 байт вместо 725 338 байт на том же срезе. Неизменившиеся позиции автобусов тоже пропускаются. Повтор маршрутов и машин в `forecast.updated` удалён. Клиент применяет пришедшие за тик патчи максимум двумя записями в кэш (маршруты и автобусы), вместо десятков отдельных обновлений React. Для официального режима данные в WebSocket обновляются раз в пять секунд, heartbeat со статусом связи — каждую секунду; REST остаётся доступен по запросу. Пятсекундный такт достаточен для горизонта прогноза 10–15 минут и явно подписан в интерфейсе. Соединение с накопленным буфером более 1 МБ закрывается и восстанавливается обычной логикой переподключения; оно не удерживает неограниченную очередь. Тест реального WebSocket проверяет полный первый тик, отсутствие неизменившихся событий во втором и компактный патч после изменения.

Проверки `tests/official-source.test.ts` моделируют 50 одновременных чтений на зависшем обновлении, последовательные отказы и восстановление, холодный старт без кэша и неполный ответ. `tests/data-flow.test.ts` проверяет, что heartbeat с `stale` удерживает предупреждение даже при последующих событиях от сохранённого снимка.

## Как воспроизвести локальный замер

Запустите `pnpm hackathon`, затем:

```sh
node scripts/benchmark-official.mjs
```

Скрипт после прогрева измеряет по 12 последовательных запросов на шесть endpoint-ов, которые обновляются вместе с интерфейсом: `/forecast`, `/routes`, `/network/summary`, `/vehicles`, `/alerts` и `/analytics/delay-series`. Затем делает четыре параллельные пачки по восемь запросов. Он считает медиану, P95, максимальную задержку, объём ответа и завершённые запросы в секунду. Отдельно один раз загружает статическую дорожную схему сайта; тяжёлый `/routes/geometry` измеряется как диагностический endpoint, а не как обычная нагрузка UI. Отдельно читаются `pipelineMs`, `inferenceMs`, число локализованных ТС и число доступных прогнозов из `/ml/status`. Для другого локального API задайте `TRANSIT_API_URL`, для сайта — `TRANSIT_SITE_URL`; размеры пачки регулируются `BENCH_BATCH_SIZE` и `BENCH_BATCHES` (ограничены в скрипте).

Проверка использует прогретые локальные процессы, официальное воспроизведение CSV и текущую машину. Она не моделирует производственную сеть, количество городских автобусов, официальный Docker-эмулятор или холодный старт контейнеров. Разные версии дорожной геометрии меняют размер ответа `/routes/geometry`, поэтому сравнивать её P95 между ревизиями как эффект одного кэша некорректно.

Для повторяемой проверки памяти шлюза при 15 подключённых клиентах:

```sh
node scripts/benchmark-ws-memory.mjs
```

Скрипт раз в пять секунд снимает RSS именно процесса, слушающего API-порт (через `lsof` и `ps`; на других ОС можно передать `BENCH_GATEWAY_PID`), и считает полученные сообщения и неожиданные закрытия. Длительность по умолчанию — 90 секунд, её можно увеличить через `BENCH_WS_SECONDS` до 600. Это проверка локального процесса с читающими WebSocket-клиентами; она не заменяет длительный тест с браузерной отрисовкой и медленной сетью.

## Замер после исправлений, 25 сентября 2026

Машина: macOS arm64, Node 24.19, прогретый официальный replay из test CSV. На финальной версии в UI-нагрузке из шести REST endpoint-ов 32 запроса пачками по 8 дали медиану 64,30 мс, P95 138,46 мс, максимум 141,84 мс и 60,13 завершённых запроса/с. Одноразовая статическая дорожная схема имела объём 419 946 байт и загрузилась за 18,22 мс; диагностический `/routes/geometry` — 539 162 байта и P95 51,35 мс по трём запросам. `/ml/status` в конце прогона сообщил `pipelineMs=116,4`, `inferenceMs=2,2`, 21 автобус с позицией и 6 прогнозов (их число меняется со временем архива). Эти показатели одного локального прогона не гарантируют задержку при другой нагрузке.

После уменьшения WS payload, но до последующей batch/delta-оптимизации интерфейса, 90-секундная проверка с дополнительными 15 WebSocket-клиентами доставила 63 465 сообщений, включая 1350 heartbeat, без неожиданных закрытий. RSS шлюза: 344,3 МБ перед подключением, максимум за измерение 344,4 МБ и 328,9 МБ в конце. В ходе прогона происходили сборки мусора (например, 306 → 279 МБ), поэтому линейного роста до лимита кучи не наблюдалось. Это короткий прогон и не доказательство отсутствия утечек при многочасовой работе.

На финальной версии **270-секундная** проверка с дополнительными 15 WebSocket-клиентами доставила 24 480 сообщений, включая 4050 heartbeat, без неожиданных закрытий. RSS шлюза: **215,2 МБ перед подключением, максимум 252,8 МБ, 238,2 МБ в конце**. Между 120-й и 130-й секундой RSS упал с 250,3 до 127,7 МБ после сборки мусора; у ряда последующих точек есть небольшие колебания. Шлюз прожил дольше прежней точки OOM (~254 с) и остался работоспособным. Это подтверждает устойчивость в данном локальном сценарии, но не доказывает отсутствие утечек при иных клиентах или многочасовом потоке.

## Протокол непрерывного замера, 26 сентября 2026

`scripts/benchmark-soak.mjs` опрашивает Backend `/status`, API `/ml/status` и `/forecast`, ML `/health`, держит читающие WebSocket-клиенты и каждые 5 секунд сохраняет RSS сервисов. В режиме NDTP статус дополнительно содержит полученные и отклонённые кадры, возраст последнего пакета, отображённые/неотображённые unit ID, число объединённых пакетов и флаг ожидающего пересчёта. Backend хранит распределение задержки последних 256 расчётов. `forecastPending` — бинарный флаг одного coalescing-события, **не размер очереди**. Счётчик `coalescedPackets` помогает обнаружить превышение частоты пересчёта, но не доказывает отсутствия потерь на внешнем TCP-источнике. Скрипт хранит все 5-секундные точки в JSON, поэтому агрегаты можно перепроверить.

```sh
BENCH_SOAK_SECONDS=1800 BENCH_SOAK_INTERVAL=5 BENCH_WS_CLIENTS=1 \
  BENCH_SOAK_OUTPUT=reports/reliability-soak.json node scripts/benchmark-soak.mjs

# Повторить с несколькими читающими WS-клиентами:
BENCH_SOAK_SECONDS=3600 BENCH_WS_CLIENTS=15 \
  BENCH_SOAK_OUTPUT=reports/reliability-soak-15-clients.json node scripts/benchmark-soak.mjs

# Для официального Docker Compose:
BENCH_RSS_MODE=docker BENCH_SOAK_SECONDS=1800 BENCH_WS_CLIENTS=15 \
  BENCH_SOAK_OUTPUT=reports/reliability-ndtp-docker.json node scripts/benchmark-soak.mjs
```

Для другого стенда доступны `TRANSIT_API_URL`, `TRANSIT_BACKEND_URL`, `TRANSIT_ML_URL`, `TRANSIT_SITE_URL` и `TRANSIT_WS_URL`. По умолчанию RSS снимается через `lsof`/`ps` у единственного локального процесса на каждом порту. `BENCH_RSS_MODE=docker` ищет контейнеры проекта `transit-hub-official` (переопределяется `BENCH_COMPOSE_PROJECT`) и читает `/proc/*/status` внутри; он записывает **максимальный RSS отдельного процесса**, а не сумму памяти контейнера. Пустое значение означает, что процесс не найден или замер недоступен. `docker stats` показывает иное потребление контейнера и не подменяется этим числом. HTTP-задержка включает передачу и разбор JSON. `pipelineMs` и `inferenceMs` — последний расчёт, прочитанный при выборке; P95 по таким точкам не является P95 каждого принятого пакета. Для NDTP нужен работающий официальный эмулятор и актуальный план, иначе `frames=0`.

Проверенный короткий прогон: процессы Backend/ML/API были запущены от коммита `f380de8` до новых правок на диске, macOS 15.7.9 arm64, Node 24.19, локальный `pnpm hackathon`, официальный CSV replay, три читающих WS-клиента, 30 секунд, шесть 5-секундных точек. Полный машинный вывод: [`reports/reliability-replay-smoke-2026-09-26.json`](../reports/reliability-replay-smoke-2026-09-26.json).

Этот первый отчёт сохранял RSS только API/Backend/ML; новый скрипт измеряет также frontend. Шесть точек слишком мало для надёжных хвостовых перцентилей и выводов о накоплении памяти. В частности, RSS API вырос на 76,2 МБ за этот интервал; требуется длинный прогон, чтобы отличить сборку мусора от устойчивого роста. Нулевой NDTP-счётчик показывает, что нагрузка настоящего эмулятора здесь не проверялась.

Для контейнерного холодного старта и восстановлений есть отдельный **изменяющий состояние стенда** сценарий. Он отказывается запускаться без `BENCH_ALLOW_DOCKER_MUTATION=1`, требует действующий `API_TOKEN` и пишет времена/сырые проверки в stdout. `cold-start` запускают только при остановленных четырёх официальных контейнерах и уже собранных образах: время не включает скачивание/сборку. `fault` требует исправно работающий контур; скрипт останавливает один сервис и гарантированно вызывает `docker compose start` в `finally`.

```sh
BENCH_ALLOW_DOCKER_MUTATION=1 API_TOKEN="$API_TOKEN" \
  node scripts/benchmark-container-lifecycle.mjs cold-start > reports/cold-start.json
BENCH_ALLOW_DOCKER_MUTATION=1 API_TOKEN="$API_TOKEN" \
  node scripts/benchmark-container-lifecycle.mjs fault ml > reports/ml-recovery.json
BENCH_ALLOW_DOCKER_MUTATION=1 API_TOKEN="$API_TOKEN" \
  node scripts/benchmark-container-lifecycle.mjs fault backend > reports/backend-recovery.json
```
