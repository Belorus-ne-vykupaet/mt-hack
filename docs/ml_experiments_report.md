# Отчёт по ML-экспериментам и дополнительным данным

## Базовая версия

За основу была взята ML-версия из `main`.

Базовая конфигурация:

- модель: `ExtraTreesRegressor`;
- 50 признаков из исходных `traffic.csv` и `schedule.csv`;
- `provided_test MAE ≈ 58.09 s`.

Все дальнейшие эксперименты сравнивались с этой версией.

---

## 1. OpenStreetMap

### Данные

Для транспортных средств и целевых остановок были добавлены признаки дорожной инфраструктуры из OpenStreetMap.

Использовались характеристики:

- количество дорог;
- количество перекрёстков;
- количество светофоров;
- количество дорог с `busway`;
- количество крупных дорог;
- количество съездов;
- количество кольцевых развязок;
- число полос;
- ограничение скорости;
- аналогичные признаки около целевой остановки.

После добавления OSM число признаков выросло:

```text
50 → 64
```

### Первый эксперимент

Изначально использовалось текущее состояние OSM, скачанное в сентябре 2026 года.

Результат:

```text
ExtraTrees

provided_test MAE:
58.09 s → 51.80 s

chronological holdout:
≈ 54.87 s
```

То есть дорожный контекст заметно улучшил качество модели.

### Historical OSM

Исходные транспортные данные относятся к январю 2026 года, поэтому использование OSM из сентября 2026 формально могло содержать изменения дорожной инфраструктуры, появившиеся позже.

Чтобы исключить temporal leakage, OSM был пересобран через historical mode Overpass API со snapshot до первой прогнозной точки:

```text
snapshot: 2026-01-06 02:04:59 UTC
```

После переобучения:

```text
provided_test MAE:      52.198 s
chronological holdout:  55.552 s
```

Результат немного хуже версии с актуальным OSM (`51.798 s`), но всё ещё значительно лучше исходного baseline (`≈58.09 s`).

В финальной версии используется именно historical OSM.

## 2. Данные выделенных полос buslanes.ru

Отдельно был протестирован датасет выделенных полос `buslanes.ru`.

Были добавлены признаки:

```text
buslane_distance_m
on_bus_lane

target_buslane_distance_m
target_on_bus_lane

buslane_corridor_frac_500m
buslane_corridor_frac_1500m

buslane_first_ahead_m
```

Число признаков увеличилось:

```text
64 → 71
```

Для оценки участка впереди между текущей позицией ТС и целевой остановкой строились промежуточные точки и оценивалась их близость к выделенным полосам.

Результат:

```text
без buslanes:
provided_test MAE = 51.798 s
chronological MAE = 54.875 s

с buslanes:
provided_test MAE = 52.285 s
chronological MAE = 55.167 s
```

Качество ухудшилось на обоих сплитах, поэтому признаки `buslanes.ru` в итоговую модель не вошли.

Вероятная причина — недостаточно точное сопоставление выделенных полос с фактическим маршрутом и направлением движения ТС.

## 3. Дополнительные внутренние признаки

Также был проведён эксперимент без новых внешних датасетов: к версии с OSM добавили дополнительные признаки, рассчитанные только из уже имеющихся `traffic.csv` и `schedule.csv`.

Добавлялись группы признаков:

- физический ETA до целевой остановки;
- требуемая скорость для прибытия по графику;
- скорость сближения с целевой остановкой;
- тренды и ускорение скорости;
- длительность текущей остановки;
- признаки направления движения;
- расстояние по последовательности плановых остановок;
- число оставшихся остановок и расстояния между ними.

Число признаков:

```text
64 → 92
```

Результат:

```text
provided_test MAE = 52.686 s
chronological MAE = 55.496 s
```

Эксперимент ухудшил качество относительно версии с 64 признаками, поэтому эти признаки в финальную модель не вошли.

## 4. Эксперименты Белоруса / Каратая

Параллельно была протестирована другая ML-схема.

На `provided test` она показывала очень низкий MAE:

```text
provided test MAE ≈ 27.42 s
```

Однако на отдельной хронологической проверке результат был значительно хуже:

```text
модель Белоруса / Каратая:
chronological MAE ≈ 59.86 s

Sasha-модель:
chronological MAE ≈ 57.80 s
```

То есть сильное улучшение на `provided test` не переносилось на другой временной участок данных.

Основная проблема состояла не в доказанном прямом leakage, а в сильном selection overfitting на `provided test`.

В процессе разработки на одной и той же тестовой выборке многократно сравнивались:

- конфигурации `ExtraTrees`;
- разные seeds;
- комбинации моделей;
- разные варианты деревьев и ансамблей.

Таким образом, `provided test` фактически использовался как validation set:

```text
модель A → test = 45
модель B → test = 37
модель C → test = 31
модель D → test = 27
```

Если многократно выбирать следующую модель по улучшению на одной и той же выборке, итоговый score постепенно подгоняется под неё даже без прямого использования target в признаках.

Поэтому результат:

```text
27.42 s
```

является реальным результатом на конкретном `provided test`, но не даёт оснований считать, что generalization модели составляет около 27 секунд.

Это подтверждается сравнением:

```text
provided test:          27.42 s
chronological stress:   59.86 s

Sasha:
chronological stress:   57.80 s
```

Дополнительно проводился аудит synthetic train на пересечения с test/validate. Было найдено и удалено порядка 295 пересекающихся строк. Это отдельно показало необходимость аккуратно контролировать синтетические данные и разбиение выборок.

По этой причине версия с `27.42 s` не использовалась как итоговая основная модель.

## Итоговая ML-версия

В итоговую конфигурацию вошли только признаки, которые дали устойчивое улучшение:

```text
модель: ExtraTreesRegressor
признаков: 64
внешние данные: historical OpenStreetMap
provided_test MAE: 52.198 s
chronological holdout: 55.552 s
исходный baseline: ≈58.09 s
```

Улучшение относительно baseline:

```text
≈ -5.9 s MAE
≈ 10%
```

В итоговую версию не вошли:

- `buslanes.ru` — ухудшение MAE;
- дополнительные внутренние признаки — ухудшение MAE;
- версия Белоруса / Каратая с `27.42 s` — сильная зависимость результата от `provided test` и отсутствие улучшения на хронологической проверке.

## Дополнительные функции проекта

### 1. Яндекс Погода с анимацией

Интеграция Яндекс Погоды реализована с наглядным отображением облачности и анимированного дождя на 3D-карте: диспетчер видит погодную обстановку по контрольным точкам сети. Проверены появление и исчезновение осадков, переключение светлой и тёмной тем, режимов 2D/3D и корректная работа элементов управления на мобильном экране. Погодный слой обновляется независимо от прогнозного ползунка и сохраняет выбранные настройки.

### 2. Яндекс Пробки и критические дорожные события

Реализован серверный адаптер Яндекс Router для выявления сильных заторов впереди автобуса, а также подключение отдельного источника ДТП и перекрытий; для живого потока предусмотрены серверный ключ и доступ к дорожным событиям. Полностью работает демонстрация «Тестовое ДТП»: событие размещается на маршруте, настоящий GigaChat анализирует ситуацию, а диспетчер получает уведомление «Задержка не определена» с рекомендацией. Автоматические и браузерные проверки подтвердили исключение событий позади автобуса и встречного направления, устранение повторов и сохранение основного ML-прогноза без изменений.

### 3. Подсказки диспетчеру от GigaChat

GigaChat анализирует ситуацию по выбранному маршруту и формирует короткие, адресные рекомендации: уточнить обстановку у водителя, проверить стоянку или рассмотреть дополнительный выпуск. Подсказки связаны с конкретными автобусами и открывают соответствующую форму действий, что сокращает путь от анализа к решению диспетчера. Проверены получение и обновление рекомендаций, привязка к автобусам, обработка ответа модели и работа интерфейса при недоступности сервиса.

### 4. Отчёты с помощью GigaChat

GigaChat формирует понятную текстовую сводку по сохранённым данным транспортной сети и выделяет действия, на которые стоит обратить внимание диспетчеру. Численные показатели вычисляются системой, а текст модели сохраняется вместе с отчётом и доступен в истории по датам. Проверены создание отчёта, сохранение результата, переключение дат и отображение на мобильном экране.

### 5. Дополнительные датасеты для обучения ML

В проект встроена модель Оли из ветки `osm-extra-trees-51`: к официальным `traffic.csv` и `schedule.csv` добавлены исторические данные OpenStreetMap о дорогах, перекрёстках, светофорах, выделенных полосах, развязках, числе полос и ограничениях скорости около автобуса и целевой остановки. Снимок OSM от 6 января 2026 года предшествует первой прогнозной точке; 14 дополнительных признаков довели их общее число до 64, а проверка на 353 примерах воспроизвела снижение MAE с 58,09 до 52,20 секунды — примерно на 10%. Дополнительно протестирован датасет выделенных полос `buslanes.ru`: сравнение вариантов позволило выбрать лучшую итоговую конфигурацию с историческим OpenStreetMap.

### 6. Движение автобусов с помощью ползунка

Непрерывный ползунок от 0 до 15 минут позволяет диспетчеру наглядно просматривать движение автобусов по маршрутам к остановкам, для которых рассчитан прогноз. Положение автобусов меняется сразу во время перетаскивания, без ожидания отпускания ползунка, и учитывает прогнозируемое время прибытия. Проверены плавное обновление в 2D и 3D, обратное перемещение ползунка и согласованность с доступным прогнозом.

### 7. Приложение для ПК и телефона

Для ПК реализована установка Transit Hub как PWA: диспетчер запускает систему отдельным приложением с рабочего стола, без ручного открытия сайта и поиска вкладки. Для Android подготовлен APK с мобильной оболочкой и адаптивным интерфейсом — готовая основа для развития мобильного рабочего места. Браузерные проверки подтвердили сценарий установки, манифест и иконки приложения, доступность скачивания APK и наличие корректного Android-пакета.

### Подтверждение реализации

Описание опирается на исходный код, воспроизводимые ML-метрики и выполненные проверки: 147 тестов TypeScript/API, 126 Python-тестов и 14 браузерных сценариев погоды, дорожных событий, GigaChat, отчётов, ползунка и установки приложения. Результат подключения модели сохранён в [протоколе интеграции](../reports/olya-ml-integration-2026-09-27.json); её веса перенесены из коммита Оли без переобучения, контрольный CSV воспроизведён с совпадением SHA-256. Подключение платного живого дорожного источника выполняется через конфигурацию сервера; тестовое ДТП явно обозначено в интерфейсе.
