# Управление движением и внешние признаки

## Что реализовано

Раздел `/dispatch` доступен через «Диспетчер» и из карточки маршрута. Два действия из ответа организаторов: изменение количества ТС на линии и изменение времени стоянки на выбранной остановке.

Первый экран диспетчера — очередь маршрутов по суммарной прогнозной задержке затронутых автобусов. Сводка показывает число маршрутов с предложением, автобусов с риском, активных демосценариев и остаток резерва. Поиск и фильтры помогают выбрать маршрут; форма плана остаётся рядом с очередью на широком экране. Подробная таблица рекомендаций и журнал решений расположены ниже. При отсутствии свежего потока применение в демонстрации блокируется, сохранение плана доступно.

Пользователь задаёт выпуск, полный оборот (оба направления и отстой), остановку и исходную/новую стоянку. Интерфейс показывает план до/после, равномерный интервал и изменение времени на одно прохождение остановки. Простой расчёт: `интервал = время оборота / число автобусов`; новый оборот меняется на разницу стоянки на одной выбранной остановке. Это допущение равномерного выпуска, не измеренный интервал между конкретными машинами и не оценка причинного эффекта ML.

В обычном демо «Применить в демо» меняет количество машин и расчётный прогноз; добавленные машины стоят на начальной остановке. Для автобусов, у которых выбранная остановка следующая и находится в пределах грубой оценки 15 минут пути, новая стоянка прибавляется к прогнозу один раз. Участки дорог не перекрашиваются из-за добавления автобуса: пробка от этого не исчезает. Деморезерв общий — 4 автобуса, уменьшение выпуска освобождает машины; это условность, не сведения перевозчика. Новое активное решение заменяет предыдущее для того же направления. Отмена восстанавливает базовый сценарий без отката других направлений.

Планы и журнал сохраняются локально в браузере. В режиме CSV/API доступно сохранение плана, факты не меняются. Реальные диспетчерские команды требуют backend API с проверкой полномочий, доступного парка/водителей, минимального интервала, посадки/высадки, обязательного отстоя и подтверждением выполнения. Эти правила не даны в кратком условии. После выдачи организаторами расширить интерфейс статусами «запрошено → принято → выполнено/отклонено» и серверным журналом, а не считать локальное нажатие фактическим выпуском.

## Имеют ли смысл внешние API

**Для короткого горизонта сначала полезнее собственная телеметрия соседних автобусов, затем дорожный трафик, затем погода.** Это инженерная гипотеза для проверки, не измеренный результат.

| Источник | Возможная польза | Ограничение | Приоритет |
|---|---|---|---|
| Другие автобусы впереди на том же участке и направлении | Ранний сигнал замедления, стоянки, сближения машин | Нужны корректные рейсы, GPS и свежесть | Высокий: уже внутри данных задачи |
| Пробки на следующих участках | Обнаружение ещё не достигнутого затора | Автобусные полосы и остановки отличаются от автомобильного движения | Проверить после базовой модели |
| Осадки, снег, температура, видимость | Дополнительный фон для времени движения/стоянок | Погода меняется медленнее горизонта 10–15 минут | Средний/низкий |
| Перекрытия, мероприятия | Сильный локальный фактор | Нужен надёжный источник, исторические версии и привязка к пути | После базовой интеграции |

Главное условие: **время внешних признаков совпадает со временем эмулятора**. Если эмулятор показывает исторический либо синтетический день, запрос сегодняшних пробок не даёт подходящий признак. Синтетическое время нельзя просто заменить текущим для объединения данных. Разрешение сторонних API не означает, что у организаторов будут ключи, квоты или доступ к интернету на стенде.

## Конкретное подключение

### Трафик

[Яндекс Router API](https://yandex.ru/maps-api/docs/router-api/request.html) принимает маршрут через точки, ключ API и настройку учёта трафика. В [ответе](https://yandex.ru/maps-api/docs/router-api/response.html) указан использованный тип трафика. Прошедшее время отправления запросом не поддерживается. Поэтому живой API не заменяет архив признаков для исторической проверки.

Предлагаемый адаптер: выбрать 2–3 ближайших впереди участка автобусного пути, получить время проезда с трафиком и без него, сформировать `traffic_extra_sec` и `traffic_time_ratio`. Проверять совпадение геометрии: автомобильный маршрутизатор может предложить объезд, тогда сравнение относится к другому пути. Не использовать пассажирский режим построения маршрутов общественным транспортом как телеметрию автобуса. Ключ хранить на backend; права хранения/использования данных и квоты проверить по выбранному договору. API сейчас не подключён и ключ не нужен для запуска сайта.

Запросы группировать по участку/направлению, а не по каждому автобусу. Кэш 60–120 секунд и ограниченная очередь — начальные параметры для измерения нагрузки. При недоступности передавать missing-признак и использовать модель без трафика, а не считать скорость свободной.

### Погода

[Open-Meteo Forecast API](https://open-meteo.com/en/docs) даёт временные ряды погодных величин. Для Москвы не следует считать интерполированную 15-минутную сетку независимыми наблюдениями. [Historical Forecast / Single Runs](https://open-meteo.com/en/docs/historical-forecast-api) позволяют работать с прошлыми запусками моделей. Для честного backtest нужно учитывать доступность запуска в момент нашего прогноза; ретроспективное фактическое значение погоды в будущем использовать нельзя.

Предлагаемый адаптер: несколько географических ячеек по городу, температура и осадки/снег, время выпуска и получения, срок действия. Обновлять редко (например, каждые 15 минут как начальная настройка), хранить серверный кэш; не запрашивать на каждую позицию автобуса. Условия использования и тариф для реального сервиса проверить отдельно. Подключение пока спроектировано, сетевого сборщика в проекте нет.

### Общий контракт и защита от утечки будущего

Подготовлен `scripts/lib/external-context.mjs`, функция `contextAt`. Запись:

```json
{
  "kind": "traffic",
  "source": "provider-name",
  "routeId": "м3",
  "availableAt": "2026-09-23T07:00:02Z",
  "validFrom": "2026-09-23T07:00:00Z",
  "validTo": "2026-09-23T07:20:00Z",
  "expiresAt": "2026-09-23T07:02:02Z",
  "values": { "travelTimeRatio": 1.4 }
}
```

Это пример контракта, не ответ внешнего API. `availableAt` — реальное время получения сборщиком; `validFrom/To` — период, к которому относится значение. Для погоды: `kind=weather`, `routeId=*` для общего городского признака или конкретный маршрут, `values.temperatureC/precipitationMm`. Если маршруты покрывают разные погодные ячейки, сборщик обязан привязать ячейку к маршруту до объединения.

Функция выбирает запись, доступную не позже выпуска прогноза, действующую на целевое время и не просроченную. При отсутствии возвращает `null` и missing-флаг; это проверяется тестами. Реальные наблюдения трафика нельзя произвольно объявить прогнозом на следующие 15 минут: для них `validTo` ограничивается временем наблюдения, а текущий трафик берётся как отдельный текущий признак с `targetAt=issuedAt`. Будущее покрытие можно задавать только если его предоставляет прогноз провайдера.

## Как решить, оставлять ли интеграцию

На одинаковом разбиении по дням/рейсам сравнить: текущая задержка → история собственной телеметрии → плюс трафик → плюс погода. Оценить MAE на +10/+15, покрытие внешними данными, худшие маршруты и время ответа. Не добавлять произвольный коэффициент «дождь = +3 минуты». Внешнюю интеграцию включать в итоговую модель только при устойчивом выигрыше. При имитационных данных, отсутствии истории или недоступности провайдера оставить её выключенной; базовая система должна запускаться автономно.
