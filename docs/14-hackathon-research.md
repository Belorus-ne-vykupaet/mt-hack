# Подготовка к хакатону Московского транспорта

Проверено 23 сентября 2026. Это предложения по развитию сервиса, а не описание уже обученной модели.

## Что известно

На [официальной странице](https://mt-hackathon.ru/#task) найден наш трек «Предиктор изменений в графике движения городского транспорта»: прогноз сбоев за 10–15 минут, поток NDTP, сопоставление с расписанием, диспетчерский дашборд. Старт мероприятия указан на 25 сентября.

Из ответа организаторов, переданного пользователем: будет Docker-образ эмулятора и описание полей; метрика — MAE по фактической задержке; расписание — кастомный CSV с маппингом на эмулятор; сторонние API разрешены. По уточнению пользователя работаем только с автобусами.

Пока не определены: протокол подключения к эмулятору (Docker сам по себе его не задаёт), единица оценки и точные горизонты, знак/единицы задержки, обработка пропусков и отмен, порог «сбоя», формат отправки предсказаний. Разрешение внешних API не подтверждает отдельно доступность интернета, ключей и квот на финальном стенде.

## Что улучшить в первую очередь

### 1. Прогноз величины задержки и честная проверка качества

Основной результат модели — задержка в секундах, например на горизонтах +10 и +15 минут. Риск для интерфейса рассчитывать поверх прогноза по настраиваемым порогам; эти пороги не выдавать за условия организаторов. Отрицательные отклонения (опережение расписания) не обрезать до уточнения целевой переменной.

До сложной модели сделать две точки сравнения: сохранение текущей задержки и историческая медиана для участка/времени суток. Затем сравнить табличную регрессионную модель с ними по одной и той же MAE. Признаки-кандидаты: текущая задержка и её изменение, скорость за последние 1/3/5 минут, время стоянки, номер остановки, оставшаяся дистанция, направление, интервал до предыдущего автобуса, час и день недели. Пользу каждого набора признаков подтвердить отдельным экспериментом.

Разделять обучение и проверку по времени, не перемешивать соседние сообщения одного рейса. Исключить признаки, появившиеся после момента прогноза. Если цель организаторов — задержка прибытия на остановку, перестроить target под остановку, а не автоматически считать это задержкой автобуса ровно через 15 минут.

Хранить неизменяемый журнал: `prediction_id`, `issued_at`, `target_at`, `vehicle_id`, `trip_id`, горизонт, версия модели, прогноз. После поступления факта сопоставлять его с прогнозом и считать MAE отдельно по горизонтам/маршрутам, число оценённых примеров и покрытие. Не считать ещё не наступившие или пропущенные факты нулевой ошибкой. На дашборде полезен блок «ошибка модели / ошибка базового прогноза».

### 2. Подключение без переделки всего сервиса

Предлагаемая цепочка:

`Docker-эмулятор → адаптер протокола → нормализованная телеметрия → состояние рейса и признаки → модель → журнал прогнозов + REST/WS → дашборд`

`CSV-расписание → проверка и маппинг полей → рейсы/остановки/плановые времена ↗`

До публикации контракта не писать предполагаемый бинарный NDTP-декодер. Изолировать формат входа в адаптере. Общая запись должна хранить время события и получения, автобус, рейс, маршрут, направление, координаты, скорость и качество данных. CSV-импорт должен проверять единицы, часовой пояс, переход рейса через полночь и неизвестные идентификаторы.

Обрабатывать дубликаты, сообщения не по порядку, скачки GPS, потерю связи и смену рейса. Прогноз пересчитывать по новым наблюдениям; частоту ограничить ресурсами стенда. Плавная анимация между сообщениями сама по себе не является новым прогнозом модели.

### 3. Полезные диспетчеру объяснения

В карточке автобуса: «Сейчас +2:10 → через 10 минут +4:30 → через 15 минут +6:00», время последнего сообщения и основные наблюдаемые факторы (падение скорости, длительная стоянка, сокращение интервала). Факторы — объяснение наблюдений, не доказанная причина задержки.

Отдельно выделять задержку участка и задержку конкретных машин; сохранять уже реализованный локальный цвет вместо окраски всего маршрута. Добавить обнаружение сближения автобусов одного направления и список растущих задержек. Интервал неопределённости показывать после калибровки на отложенной выборке. Текущие демонстрационные проценты риска не выдавать за точность модели.

### 4. Пробки и погода как проверяемое дополнение

Подключать внешние признаки после работающей базовой модели: с кэшем, таймаутом, временем актуальности и признаком отсутствия данных. Проверить, уменьшают ли они MAE. Без внешних API базовый прогноз должен продолжать работать. Историческую проверку проводить на данных, которые были доступны в момент прогноза, а не на сегодняшних пробках или будущем факте погоды.

## Датасеты для подготовки

### Dublin Bus GPS — наиболее близкий по структуре

[Dublin City Council / data.gov.ie](https://data.gov.ie/en_GB/dataset/dublin-bus-gps-sample-data-from-dublin-city-council-insight-project). Автобусная телеметрия: время, координаты, маршрут/рейс, автобус, остановка, признак стоянки и задержка в секундах (со знаком). Есть архивы ноября 2012 и января 2013; каталог указывает CC BY 4.0. [Страница январского архива](https://data.smartdublin.ie/dataset/dublin-bus-gps-sample-data-from-dublin-city-council-insight-project/resource/00c65697-9ed6-43cb-a2b7-9e20cf323cb3).

Предлагаемое применение: воспроизведение потока, оконные признаки и прогноз будущего поля Delay по рейсу. Данные старые, распределение отличается от Москвы. Сначала проверить частоту, пропуски, единицы timestamp, знак задержки и целостность рейсов. Не переносить результат MAE напрямую на московский стенд. Проверены описания каталогов; полные архивы не скачивались и не проходили аудит.

### Switzerland Actual Data v2 — план и факт по остановкам

[Официальный каталог SKI](https://data.opentransportdata.swiss/en/dataset/ist-daten-v2), [описание полей](https://opentransportdata.swiss/en/cookbook/historic-and-statistics-cookbook/actual-data/). Ежедневные CSV с рейсами, остановками, плановыми и фактическими/прогнозными временами. Отфильтровать автобусный тип по `PRODUKT_ID`.

Критично: поле времени может содержать последний прогноз, оценку или реальный факт. Для строгой фактической цели использовать соответствующий `AN_PROGNOSE_STATUS` / `AB_PROGNOSE_STATUS = REAL`; `FORECAST`, `ESTIMATED`, пустые и `UNKNOWN` не смешивать с ним. Источник подходит для задержки на остановках, но не заменяет непрерывную GPS-телеметрию. Расписание округлено до минут, что ограничивает точность цели. Проверены каталог и документация, не обучающая выборка. Соблюдать [условия использования](https://opentransportdata.swiss/en/terms-of-use/).

Оба источника использовать для прототипирования отдельно от официальной оценки. После выдачи данных организаторов сверить правила использования внешнего обучения и измерять финальное качество на их данных.

## Порядок работы команды

1. До старта: общий формат телеметрии, адаптер CSV, воспроизводимое проигрывание истории, базовые прогнозы и журнал оценки.
2. После выдачи образа: подключение реального протокола и полей, воспроизведение запуска через Docker Compose, уточнение целевой переменной и MAE.
3. Затем: признаки истории рейса, обучение, сравнение с базовыми прогнозами, карточка объяснений и контроль свежести.
4. В последнюю очередь: внешние API и более сложные модели, только при измеримом улучшении.
