# Поток NDTP: доставка и состояние дверей

Проверка относится к официальному контуру из четырёх сервисов. Это технические результаты; баллы ставит жюри. Сценарий и определение метрик — в [30-минутной проверке парка](25-bi-and-fleet-validation.md).

## Что исправлено

- API проверяет снимок официального Backend раз в секунду и передаёт новый GPS ближайшим тактом WebSocket. Раньше он намеренно ждал до пяти секунд между пачками.
- Версии сообщений учитывают новые координаты, наблюдённую задержку, риск, целевую остановку и состояние дверей. Изменение только секундного отсчёта и малый дрейф прогноза не заставляют отправлять весь парк заново.
- Пакет NDTP `G6CellIrma04` (тип 4, 15 байт) разбирается по структуре, проверенной на образе организаторов: одометр, зона, счётчики входа/выхода и биты присутствия/закрытия четырёх дверей. Если установлена хотя бы одна дверь, Backend выдаёт `doors_open=true/false`; без датчика значение `null`. Карточка ТС показывает состояние только при известном измерении, а при старом GPS подписывает его как последнее известное.
- Пакет запускает пересчёт Backend сразу. Периодический запрос неизменённого снимка не запускает второй прогноз всего парка каждую секунду; при отсутствии пакетов возраст и статус обновляются не позднее следующего пятсекундного пересчёта.
- Измеритель потока считает частоту по временному интервалу между первой и последней выборками, а не по номинальной длине прогона.

Статус дверей виден рядом с текущим участком и целевой плановой остановкой. В архивных CSV нет этих битов, поэтому историческая модель по ним не обучалась; открытие дверей само по себе не объявляется причиной задержки или подтверждённым прибытием.

## Повторяемые наблюдения

[JSON короткого замера](../reports/reliability-fleet-stream-2026-09-26.json): 100 ТС, пакет от каждого каждые 5 с, 15 читающих WebSocket-клиентов, 120 с на контейнерах. В этом замере уже работали новый такт, подавление повторов и пятсекундный кэш Backend. Поддержка IRMA добавлена после замера; она не меняет расчёт прогноза для пакетов без IRMA. Хеши измеренных исходников находятся внутри JSON.

| Метрика | P95 / результат |
|---|---:|
| GPS timestamp → первое обновление у WS-клиента | 3,63 с |
| Полный расчёт Backend | 1,54 с |
| Вызов ML | 0,50 с |
| Новые кадры NDTP | 19,94/с |
| Ошибки HTTP/NDTP и неожиданные разрывы WS | 0 |

Для сравнения исходный [30-минутный замер](25-bi-and-fleet-validation.md) зафиксировал P95 GPS→WS 10,69 с при прежнем пятсекундном такте. Двухминутный прогон подтверждает ускорение и отсутствие ошибок в этом интервале; он не заменяет 30-минутную проверку устойчивости или проверку под удалённой сетью.

Разбор IRMA проверен тестом на бинарном пакете с битами открытой/закрытой двери и живым образом `ndtp-telemetry-emulator:1.0`: для сопоставленного устройства API выдал сначала `true`, затем `false`. Неподключённый датчик остаётся `null`. Полный набор проверок после изменений: **126 frontend/API-тестов**, **114 Python-тестов**, типы, lint, production-сборка и три официальных браузерных сценария (основная карта, темы, журнал факта и прогноза, восстановление после отказа).

Полная сборка `docker compose -f compose.official.yaml build` после очистки контекста завершилась успешно. `docker compose -f compose.official.yaml up -d --no-build --force-recreate` поднял новые образы без подключений к исходным папкам; ML, Backend и API стали `healthy`, сайт и три HTTP-проверки ответили 200. Загрузка зависимостей на проверявшей машине была медленной и один раз оборвалась; кэш и повтор установки в Dockerfile позволили завершить чистую сборку.
