# Проверка горизонта раннего предупреждения

## Что считается событием

Сервис предупреждает о **возможном превышении опоздания на 120 секунд** на конкретной плановой остановке `tt_action_item_id`. Пороговая отметка этого события — `event_time = time_begin + 120 с`, `event_type = late_threshold`. Эта отметка известна из расписания до прибытия автобуса. Само событие подтверждается позже, если фактическое прибытие оказалось позже плана более чем на 120 секунд; иначе предупреждение считается ложным.

У прогноза и предупреждения два разных времени, которые нельзя подменять друг другом:

1. **ML-прогноз прибытия** сохраняет официальный горизонт `600 < time_begin − T <= 900 с`. Модель, признаки, её цели и сабмит не изменены.
2. **Первое предупреждение** дополнительно требует `600 < event_time − T <= 900 с`. Пересечение двух условий — `600 < time_begin − T <= 780 с`. Когда плановая цель находится дальше 780 секунд, прогноз и оценка риска уже доступны, а первое предупреждение ожидает входа в окно события. Время выпуска не переносится назад.

Поэтому первое предупреждение находится за **12–15 минут до потенциального превышения порога**, внутри требуемого окна 10–15 минут. Это явное рабочее определение события. Неизвестное будущее **фактическое прибытие** может оказаться позже; гарантировать окно ровно 10–15 минут до него нельзя. Если жюри определяет «событие» именно как фактическое прибытие, приведённая проверка не заменяет эту иную трактовку.

## Часы и причинность

| Поле предупреждения | Смысл |
|---|---|
| `issued_at` / `created_at` | Неизменное время первого выпуска для пары ТС/цель |
| `target_time` | Плановое прибытие на целевую остановку |
| `expected_arrival_at` | План + текущий прогноз опоздания; может обновляться |
| `event_time`, `event_type` | Отметка `план + 120 с` и тип `late_threshold` |
| `forecast_horizon_sec`, `lead_time_sec` | Запас до плана при первом выпуске; legacy-поле `lead_time_sec` сохраняет прежний смысл |
| `event_lead_time_sec` | Запас до пороговой отметки при первом выпуске |
| `current_forecast_horizon_sec`, `current_event_lead_time_sec` | Текущие обратные отсчёты; не меняют первый выпуск |

Время из CSV сравнивается без перевода часового пояса. Телеметрия и факты прибытия, доступные для расчёта в момент `T`, ограничены временем `<= T`. Целевая остановка, достижение которой уже наблюдалось, исключается. В архиве это `time_fact_begin <= T` для той же записи плана; в NDTP используются уже принятые наблюдения GPS. Будущие фактические прибытия **не участвуют** в выборе окна или выпуске сигнала. Чистая функция [`warning_timing`](../ml/transit_ml/warnings.py) вообще не принимает фактическое прибытие.

Повторный расчёт обновляет прогноз, но не создаёт новый «первый» алерт и не исправляет историю задним числом. `/warnings/audit` в Python Backend содержит метаданные первого выпуска и добавляет фактический результат только после его наступления в архиве. Карточка отделяет план, ожидаемое прибытие, пороговую отметку и наблюдаемый фактор; последний не выдаётся за причинное объяснение модели.

В живом режиме пакет известного `unit_id` вызывает пересчёт без опроса из браузера. Частые пакеты объединяются: не более одного расчёта в секунду. Неизвестный `unit_id` учитывается в `/status.ndtp.unmappedPackets` и не порождает ТС/алерт. GPS старше 180 секунд оставляет последнюю позицию с пометкой `stale_gps`, без прогноза; пакет старше последнего принятого от устройства отбрасывается. Некорректный CRC учитывается как ошибка. Резервная оценка при отказе ML помечается `fallback` и отдельно учитывается в журнале. Живой режим требует `LIVE_PLAN_DIR` с `schedule_plan.csv` и `unit-map.json`; январское расписание на текущую дату не переносится.

## Воспроизводимый аудит

После подготовки данных и сборки актуальных образов по [инструкции для жюри](../JURY_QUICKSTART.md):

```sh
docker compose -f compose.official.yaml run --rm --no-deps -v "$PWD/scripts:/app/scripts:ro" backend python /app/scripts/audit-early-warnings.py > early-warning-audit.json
```

Аудит запускает реальный Backend и модель на последовательных срезах потока. Он проверяет горизонт **всех прогнозов**, оба окна **всех первых предупреждений, включая ложные**, корректность объявленных часов и неизменность первого выпуска. После инференса фактические прибытия используются для подсчёта обнаружений, пропусков и ложных сигналов. Нарушение любого временного контракта, изменение первого выпуска или отсутствие предупреждений завершает команду с ненулевым кодом.

Свежий машинный результат: [`reports/early-warning-audit-2026-09-26.json`](../reports/early-warning-audit-2026-09-26.json), запуск **26.09.2026 13:45:13 UTC**. Модель `sasha-extra-trees-v2`, официальный `test`, архивное время **06.01.2026 17:50–18:35**, шаг **30 секунд**.

| Проверка | Измеренный результат |
|---|---:|
| Срезы / доступность модели | 91 / 91 |
| Уникальные первые предупреждения | 95 |
| Запас до плана при первом выпуске | 630–780 с |
| Запас до объявленного события, все первые предупреждения | 750–900 с; медиана 780 с, P95 900 с |
| Первые предупреждения вне окна события | 0 |
| Прогнозы или первые предупреждения вне планового окна | 0 |
| Изменения времени первого выпуска | 0 |
| Предупреждения после фактического прибытия | 0 |
| Истинные поздние события, предупреждённые в окне события | 92 / 120 — 76,67% |
| Пропущенные поздние события | 28 |
| Ложные сигналы среди оценённых предупреждений | 3 / 95 — 3,16% |

**Знаменатель сохранён от предыдущего аудита:** все уникальные записи плана с `time_begin` в **(18:00, 18:50]** и известным фактом, включая ТС без пригодного GPS. Таких целей **199**, поздних событий **120**. Знаменатель не сужен до нового окна предупреждений и не отбирается по успешным прогнозам. Из **105** поздних событий, для которых хотя бы на одном срезе имелся готовый прогноз, заранее обнаружены **92/105 — 87,62%**. Это дополнительная метрика; основная остаётся **92/120**.

Запас до **фактического прибытия** измерен отдельно: минимум **745 с**, медиана **1028 с**, P95 **1186,2 с**, максимум **1345 с**. Он не выдаётся за запас до порогового события. JSON содержит все **199** оценённых событий и все **95** первых предупреждений, включая их часы и исходы. Доля **3/95** — ложные среди предупреждений, не специфичность модели. Предоставленный `test` участвовал в выборе модели, поэтому этот прогон не является независимой оценкой качества.

## Регрессионные проверки и NDTP

[`ml/tests/test_warning_window.py`](../ml/tests/test_warning_window.py) проверяет границы **600/780/900 секунд**, отложенный первый выпуск, неизменность первого выпуска и отдельные текущие отсчёты. Синтетический replay-тест реального `Engine` подтверждает, что прогноз и риск уже доступны при горизонте 900 секунд, предупреждение публикуется при 780 секундах, а замена будущего факта с позднего прибытия на раннее **не меняет ни запрос инференса, ни предупреждение**. При горизонте ровно 600 секунд новая цель не прогнозируется. На указанном прогоне прошли **17/17** тестов этого файла.

Бинарные TCP-тесты дополнительно проверяют фрагментацию кадра, CRC, повторное соединение, пересчёт по пакету без UI, неизвестный ID, потерю свежего GPS и запоздавший пакет. [Исходный smoke-тест официального эмулятора](../reports/ndtp-emulator-smoke-2026-09-26.json) подтвердил цепочку `G6CellNav00 → Backend → ML → REST/WS → браузер` в Docker. Этот сохранённый smoke выполнен **до уточнения окна события**: его предупреждение за 860 секунд до плана не является доказательством нового временного контракта. Для синтетического live-плана без фактических прибытий точность и запас до факта не измеряются; архивный аудит выше проверяет их отдельно.
