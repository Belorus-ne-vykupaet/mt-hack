# Проверка горизонта раннего предупреждения

Официальное условие требует прогноз или алерт в окне T+10…15 минут до события, без предупреждений задним числом и на потоке. Цель сервиса — конкретная запись планового прибытия `tt_action_item_id`; окно задано строго как `600 < time_begin − T <= 900` секунд. Время из CSV сравнивается без перевода часового пояса. Телеметрия для признаков ограничена `event_time <= T`.

При каждом срезе исключается целевая остановка, фактическое достижение которой **уже наблюдалось** к T. В архиве это `time_fact_begin <= T` для той же записи плана. В NDTP это остановившийся в пределах 50 м автобус, увиденный за последние 30 минут. Будущие фактические прибытия не используются для решения, выпускать ли сигнал. Время первого выпуска алерта хранится неизменным для пары ТС/цель; повторный расчёт обновляет величину прогноза, но не создаёт новый «первый» алерт. В карточке видны целевая остановка, плановое и ожидаемое прибытие, запас времени на момент первого сигнала и **наблюдаемый фактор**, который не выдаётся за причинное объяснение модели. `/warnings/audit` в Python Backend показывает первый выпуск и, по мере наступления события в архиве, его фактический результат.

В живом режиме входящий NDTP-пакет вызывает перерасчёт автоматически, даже когда браузер не опрашивает API. Частые пакеты объединяются: не более одного расчёта в секунду. Пакет старше 180 секунд не даёт прогноз; задержанный пакет не переиздаёт алерт после закрытия окна. При отказе ML резервная оценка помечается как `fallback` и отдельно видна в журнале.

Воспроизведение проверки:

```sh
PYTHONPATH=ml ml/.venv/bin/python scripts/audit-early-warnings.py
PYTHONPATH=ml ml/.venv/bin/python -m pytest ml/tests/test_fleet.py ml/tests/test_ndtp.py ml/tests/test_pipeline.py ml/tests/test_features.py -q
```

Результат на официальном `test`, архивное время **06.01.2026 17:50–18:35**, шаг **30 секунд** (запуск 25.09.2026): **91** срез, модель доступна на **91/91**; **101** уникальное первое предупреждение. Запас времени до плановой цели при первом выпуске: **630–900 секунд**. Для всех **101** есть фактическое прибытие для последующего аудита; ни один сигнал не выпущен после планового окна или после фактического прибытия. Тесты с пропущенным, запоздавшим NDTP-пакетом и достижением цели раньше плана также проходят.

Это проверка работы на архивном воспроизведении и синтетическом NDTP-потоке. Реальный Docker-эмулятор организаторов и полный длительный поток им ещё не проверены, поэтому она не гарантирует оценку жюри 4/4. Число 101 не является полнотой обнаружения всех будущих задержек: здесь проверялись своевременность и причинность **выпущенных** предупреждений, а не recall.
